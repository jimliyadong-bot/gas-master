## 1. 修复结果与评审历史

| 问题 | 当前修复 | 固定回归证据 |
|---|---|---|

**R1响应契约**：`H5StationController` 仅对已绑定DTO的参数校验失败及事务服务抛出的 `ServiceException` 返回 `stationWriteAttemptRejected: true` 和原 `requestId`。该标记只证明**本次尝试**被拒绝，不证明此前未知尝试未提交；首次新尝试且请求号匹配才可解锁。数据库／提交等通用异常不标记。旧版后端没有标记时前端保守锁定，因此应配套部署。持续无法查明结果时保留凭据并核查原单，不通过清理存储或换号规避。

**以下是修复前的缺陷记录**：位置行号为评审时快照，不代表当前源码仍有这些问题；当前结果以上表及§8为准。

### R1 · P1：未知结果在后续重试失败时被错误解锁，可造成重复入库

**位置**：

- [ManagerBatch.vue:119–121](../h5/src/views/ManagerBatch.vue#L119)：收到任意 `businessCode` 就调用 `draft.rejected()`、解锁字段。
- [ManagerBatchCreate.vue:67–69](../h5/src/views/ManagerBatchCreate.vue#L67)：新建采购有相同处理。
- [request.js:25–32](../h5/src/api/request.js#L25) 为所有非零业务响应设置 `businessCode`；[station-draft.js:29–36](../h5/src/utils/station-draft.js#L29) 在解锁后字段变化时生成新请求号。

**复现与影响**：

1. 采购量 100，提交到货 20；服务端已保存，但成功响应丢失，页面进入“结果未确认”。
2. 原请求重试时，在查明幂等记录之前发生数据库异常，返回 HTTP 200、`code=500`。现有全局异常处理器会将运行时异常和业务异常都包装成错误响应，不能从这个 code 推断原提交是否成功。
3. 页面解锁数量／备注；操作人以为未入库，更改备注后重试。
4. 新请求号被视为另一笔到货，累计量仍低于采购上限，因而额度校验不能防止重复入库。

**修复前证据**：Chromium API mock 复现了同一笔 20 的到货变成两条入库、合计 40；不是实际数据库写入。采购创建同样存在更换请求号重复建批的风险。

**修复建议与通过条件**：未知结果不能被后续一次通用错误覆盖。应保留原请求号、原载荷及锁定状态，直到查明该逻辑请求的权威结果；仅当确定原请求未生效时才允许更正换号。补“响应丢失 → 重试系统错误／权限变化 → 再次重试”的采购、补货回归；最终只能有一个结果 ID、一笔入库增量。不要用清理 sessionStorage 作为解决办法。

### R2 · P2：跨标签页切换身份后，确认站点与实际创建站点可能不一致

**位置**：[ManagerBatchCreate.vue:41–46、59–65](../h5/src/views/ManagerBatchCreate.vue#L41) 初始化时保存站点和凭据命名空间，但提交前未检查身份变化；[request.js:10–14](../h5/src/api/request.js#L10) 每次请求临时读取共享 `localStorage` 中的最新 token。

**复现与影响**：A 站管理员打开创建表单；同源另一标签页切换为 B 站管理员；原页面和弹窗仍显示 A 站，提交却携带 B 的身份。后端按合法 B 身份归属批次，结果落在 B 站，与本人确认内容不一致，提交凭据还保存在 A 的本地命名空间。

**修复前证据**：两个同源标签页的 API mock 检查重现“弹窗 A 站、POST 使用 B 身份、创建 B 站批次”。这是身份切换后的表单一致性问题，**不是已经证明后端允许 A 身份越权写 B 站**。

**修复建议与通过条件**：表单、凭据和请求应绑定同一身份版本；检测到账号／站点／token 变化时禁止旧表单继续发送，重新加载并让本人核对。确认弹窗期间切换也必须覆盖；不能仅在页面首次进入时检查。

### R3 · P3：额度浮点相减在合法大数量边界误拒绝刚好补满

**位置**：[ManagerBatch.vue:61、106](../h5/src/views/ManagerBatch.vue#L61)：额度使用 `Number` 相减，提交比较只补偿 `0.000001`。

**复现**：采购量 `10000000000.05`、累计到货 `10000000000.04`，合法剩余额度为 `0.01`；单价 `0.0001` 时采购金额也在允许范围内。实际 JS 差值为 `0.009998321533203125`，页面显示 `0.01`，提交 `0.01` 却提示超量，且不发送请求。

**修复前证据**：数值计算和 API mock 页面均重现。主要影响允许范围内的大数量边界，不是日常小数量必现问题。

**修复建议与通过条件**：数量比较改为两位小数定点整数／十进制运算，不靠扩大浮点容差；补最大数量附近“刚好到满”和“多 0.01”测试。

### 已检查的设计与尚未证明的部分

- 服务方法均调用实时站管身份检查；不调用开班／当班检查。站点、采购商、操作人和金额不由写请求任意指定。
- 幂等表按站点＋用户＋操作＋请求号唯一，载荷有指纹；幂等结果和业务写入位于同一事务。
- 共享入库按采购批次 → 库存池 → 到货记录加锁，校验累计到货毛量；采购数量不能缩到累计到货以下。
- CNG／LNG 页面单位分别为 m³／kg，库存没有跨气种合并。
- **上述最初为源码检查。** 后续已将服务数据库测试从8项扩至14项，并新增6项真实HTTP／浏览器测试，覆盖混合业务服务入口并发、已有池回滚、LNG／同采购商多站、分页、JWT／Shiro／MVC与响应契约。详细执行证据及未覆盖项见§10，不把共享后台业务服务调用等同于后台页面验收。

## 2. 验收边界与准入条件

### 2.1 本阶段验收什么

站管入口 → 本站库存／采购查询 → 建立采购批次（不入库）→ 录入实际到货 → 本人确认 → 到货、库存池、IN 流水及幂等结果一致。

必须满足：仅本站站管可操作、不要求当班、取消不写入、同一逻辑提交不重复、累计到货不超过采购量、销售消耗／库存调整不恢复到货额度、无第二人审核。

不验收为 M1 成果：M2 库存不足记账、核验凭据、退款、真实支付／短信、额外付款／票据写权限、生产上线。原型 `design/prototypes/` 也不是本次实际 H5 验收对象。

| `exactQuotaAndDuplicateReceiptOnlyIncreaseOnce` | 分次到满、重放不增加、载荷冲突、超量拒绝 |
| `overLimitRollsBackPoolReceiptLedgerAndRequest` | 首次超量不留下到货、池或请求记录 |
| `enclosingFailureRollsBackAllAndSameRequestCanRetry` | 外层事务失败回滚，原请求可重试 |
| `scopesQueriesAndRejectsOtherStationMemberStaffAndRevokedAdmin` | 查询／写入站点范围、角色取消 |
| `concurrentSameRequestProducesOneReceipt` | 同请求并发只一笔到货 |
| `concurrentDifferentRequestsCannotExceedQuota` | 剩余额度不足容纳两笔时，仅一笔成功 |
| `consumedStockDoesNotRestoreQuotaAndBatchCannotShrink` | 消耗不恢复额度，禁止缩到累计到货以下 |

本轮新增6个方法：已有池完整快照／孤立流水回滚、并发20+20刚好补满、后台共享服务与H5抢额度、缩量与到货竞争、跨批次首次建池／跨站并发、负调整不恢复到货额度。`assertStock`也增加逐条到货与IN流水的数量、归属、操作人检查。

这14项仍是服务测试；真实HTTP与浏览器由新增`GasH5StationHttpTest`另行验证，见§10。

### 6.1 接口与请求样例

| 方法 | 路径 | 检查点 |
|---|---|---|
| GET | `/api/h5/m/overview` | 本站采购商与按气种库存 |
| GET | `/api/h5/m/batches?page=1&size=10&gasType=CNG&batchNo=PB` | 本站分页／筛选；total 与 rows 一致 |
| POST | `/api/h5/m/batches` | 创建批次、不入库 |
| GET | `/api/h5/m/batches/{batchId}` | 本站批次详情及气种库存 |
| GET | `/api/h5/m/batches/{batchId}/receipts?page=1&size=10` | 本批次、本站的到货分页 |
| POST | `/api/h5/m/batches/{batchId}/receipts` | 实际到货、事务与幂等 |

使用本机安全会话中的 `Authorization: Bearer …`，JSON 写请求带 `Content-Type: application/json`，同时带 `X-Requested-With: XMLHttpRequest` 和 `Accept: application/json`。不要把 token 粘贴进文档或上传未脱敏 HAR。业务成功判断为 **`code=0` 且结果 ID／内容正确**，不是只看 HTTP 200。

创建示例；每轮首次提交替换 `r01`，原请求重试时不要改：

```json
{"requestId":"m1-20261120-r01-create-a","gasType":"CNG","purchaseDate":"2026-11-20","qty":"100.00","unitPrice":"3.0000","remark":"M1-20261120-r01"}
```

取得实际 batchId 后，到货示例：

```json
{"requestId":"m1-20261120-r01-receive-a-01","qty":"60.00","receivedAt":"2026-11-20 10:00:00","remark":"M1-20261120-r01"}
```

日期／时间按测试场景设置，格式分别为 `yyyy-MM-dd`、`yyyy-MM-dd HH:mm:ss`，核对 GMT+8；请求号为8—64位字母、数字、下划线或短横线。不要使用含中文／尖括号的占位值作为实际请求号。

### 6.3 重试、存储及故障

| 编号 | 故障注入步骤 | 通过标准 |
|---|---|---|
| ERR-01 | 连续点击提交／确认；原请求并发发送 | 同一逻辑提交只有一个 batchId／receiptId 和一次库存增量 |
| ERR-02 | **后端提交成功之后**丢弃响应，再刷新并原样重试；另测刚好到满时响应丢失 | 保留原号原内容；即使额度已满仍能重试取得原结果；不再入库。单纯在发送前断网不能代替此测试 |
| ERR-03 | 按 R1：丢失成功响应 → 原号重试通用错误 → 本次明确拒绝 → 刷新 → 再重试 | 全程不解锁、不换号；仅一个结果和一次增量。固定mock回归已通过，真实账本待核对 |
| ERR-04 | 首次新尝试收到明确拒绝标记及匹配requestId，允许更正字段后重提 | 可更正且只新增更正后的有效记录；只有通用code=500不能解锁，此前存在未知尝试时即使带拒绝标记也不能解锁 |
| ERR-05 | 发送前令 sessionStorage.setItem 失败；另预置损坏JSON／不合法结构 | 不发送新写请求；保留原坏记录，不静默清空后重建 |
| ERR-06 | 服务端成功后令本地 removeItem 失败，或令后续详情刷新失败 | 明确“已成功、待刷新核查”，不能显示整体入库失败诱导重录；再次进入可用原键查明 |
| ERR-07 | 按 R2：填写后、弹窗期间、实际发送前及响应返回前切换身份；覆盖同标签页和跨标签页 | 未发出的旧提交被阻止；已发给原身份的结果不可误用于新身份，保留原凭据；恢复原账号后原号重试。不能落到弹窗未确认的站点 |
| ERR-08 | 按 R3 的大数量边界补0.01，再试多0.01 | 刚好到满可提交；超量拒绝；两位小数定点比较 |

故障注入优先用本地受控测试代理／Playwright 路由或专用测试桩，不通过停掉共享 MySQL、删业务表或修改生产配置来模拟。API mock 可检查页面状态，但“实际只写一次”还必须在隔离库核对。

### 6.4 数据库事务与并发

| 编号 | 并发／回滚场景 | 通过标准 |
|---|---|---|
| TX-01 | 同用户、同请求号、同内容同时到货60 | 两请求返回同 receiptId；1条到货、1条IN、1次total_in增量 |
| TX-02 | 采购100，两不同请求同时各到货60 | 仅一笔成功；累计60；另一笔额度拒绝，不留半成品请求或账本 |
| TX-03 | 剩余额度40，两不同请求分别20并发 | 都成功；刚好到满；无丢更新 |
| TX-04 | H5到货与后台既有到货入口竞争同批次额度 | 共用上限有效，不能因入口不同超量 |
| TX-05 | 到货与后台缩采购量并发 | 串行结果满足累计到货≤采购量；失败方明确反馈；不接受两者都成功造成超量 |

本轮14项服务测试已覆盖TX-01—07所列核心场景；其中TX-04直接并发调用后台复用的`IInventoryService.receive`和H5服务，不是后台HTTP／Thymeleaf操作。真实HTTP幂等及H5提交后断响应链路另见§10。并发测试只证明实际运行的调度结果，不是穷尽所有交错或死锁故障的形式化证明。

## 7. 数据对账：避免只看成功提示

在已确认隔离库执行。将下列变量改为本轮创建的真实 ID；它们只用于查询，示例值不是已有数据的默认目标。

```sql
SET @m1_station = 123; -- 替换为本轮测试站点
SET @m1_batch = 456;   -- 替换为本轮测试批次

SELECT b.batch_id, b.station_id, b.buyer_id, b.gas_type, b.qty, b.amount,
       (SELECT COALESCE(SUM(r.qty),0) FROM gas_purchase_receipt r WHERE r.batch_id=b.batch_id) AS received_qty
FROM gas_purchase_batch b WHERE b.batch_id=@m1_batch AND b.station_id=@m1_station;

SELECT r.receipt_id, r.batch_id, r.station_id, r.gas_type, r.qty, r.received_at, r.create_by,
       (SELECT COUNT(*) FROM gas_inventory_ledger l WHERE l.receipt_id=r.receipt_id AND l.biz_type='IN') AS in_rows,
       (SELECT COALESCE(SUM(l.qty),0) FROM gas_inventory_ledger l WHERE l.receipt_id=r.receipt_id AND l.biz_type='IN') AS in_qty
FROM gas_purchase_receipt r WHERE r.batch_id=@m1_batch AND r.station_id=@m1_station;

SELECT p.pool_id, p.gas_type, p.total_in, p.reserved, p.consumed, p.adjusted,
       p.total_in+p.adjusted-p.consumed-p.reserved AS available,
       (SELECT COALESCE(SUM(l.qty),0) FROM gas_inventory_ledger l WHERE l.pool_id=p.pool_id AND l.biz_type='IN') AS ledger_total_in
FROM gas_inventory_pool p WHERE p.station_id=@m1_station;

SELECT station_id, user_id, operation, request_id, result_id, create_time, completed_at
FROM gas_station_write_request WHERE station_id=@m1_station ORDER BY create_time;
```

核对：

- 每条新到货恰好对应一条 IN，数量相同，pool 的站点／气种匹配；流水 operator 与到货 create_by 一致。
- `total_in = 对应池所有 IN 数量合计`；可用量按 `total_in + adjusted - consumed - reserved`，不是直接等于批次剩余额度。
- 新批次累计到货不超采购量；幂等 result_id 指向原批次／到货；拒绝／回滚没有本轮写入残留。
- 回滚检查要比较前后池和流水原始记录，不能仅通过 join 存在的池来排除孤立流水；已有池不应被删除或重置。
- H5、后台及上述 SQL 三方一致；CNG 与 LNG、A/B/C 各站分别核对，不合并求和。

手工测试数据清理由测试负责人按本轮确定的 ID 和依赖关系处理，或销毁整个专用临时库。不要通配删除业务记录、随意清空幂等表或用初始化脚本重置存量库。
