# 专业任务模板与交接约定

> 版本：T-v1.0｜日期：2026-11-21｜适用：手动与自动SOP，按任务选用。
>
> 本文只补充“专业任务怎么做、产物怎样接上下一步”。质量与放行仍以[共用质量标准](开发质量门禁与正确性验证标准.md)为准，调度与授权仍由两份SOP规定。**这不是已安装的Skill、12-Agent团队或可运行编排器。**

<a id="task-routing"></a>

## 0. 按需加载，不增加操作者负担

| 当前需要 | 使用模板 | 不需要做的事 |
|---|---|---|
| 新界面、视觉改造或复杂交互 | [UI设计与交付](#ui-task) | 不为每次文案修复重建完整原型工程 |
| 前后端实现或接口联调 | [实现与集成](#implementation-task) | 不按模板另选技术栈、另建一套代码目录 |
| 测试设计、执行与缺陷复查 | [QA验证](#qa-task) | 不默认运行与任务无关的全部平台测试 |
| 原因不明或反复出现的缺陷 | [根因诊断](#debug-task) | 不把每个普通修复都转交新Agent |

- AI按任务选择相关片段，不要求用户管理角色或搬运文件；需求梳理继续使用既有SOP，不新增整套PM文档。
- 项目规范、批准需求／设计、实际技术栈和目录映射优先。模板只能细化获准任务，不能产生新权限、改变业务规则或降低质量门槛。
- 同一会话可承担多个专业职责，但**切换人设不等于独立Review**。需要独立审查时仍使用获准的独立上下文或合适人工；本文件不授权额外Agent。
- 维持单写入者。UI原型、业务代码、测试代码的编辑均须属于获准文件范围；QA若需改测试，也要纳入写入安排。Review不修改受审代码，报告由获准的记录者落盘。
- 模板版本、当前输入和交接记录可嵌入已有任务卡／执行记录，不强制建立新目录、新表单或第二套事实源。

## 1. 统一交接：上一步的产物必须能被下一步使用

### 1.1 最小交接记录

```markdown
- 任务／阶段／所用模板版本：
- 输入依据：需求、设计、接口、源码等实际位置与相关版本／摘要；待确认项：
- 产物：实际路径或可访问入口、版本／摘要、产出者；未产出不能填已完成：
- 接收方／用途：下一任务或审查职责，不必是另一个Agent：
- 接收检查：存在且可读取、版本匹配、内容满足约定；需用户确认的依据：
- 限制与下一步：已验证／未验证、缺项、恢复动作；由谁补齐：
```

交接前实际读取／打开产物，不仅检查文件名。输入更新后核对影响；截图、API定义和报告过期时不能继续冒充当前依据。自动模式由控制器核对交接与依赖条件，不让产物作者一句“可用”直接推进状态；手动模式如实记录人工／当前会话核对。

**产物可被下游使用，不等于任务技术通过、用户验收或发布许可。** 可以接收带明确限制的草稿用于规划，但不能用它满足要求“已批准／已验证”的依赖。

### 1.2 三条关键交接链

| 从哪里到哪里 | 必须能接上的内容 | 谁补缺项 |
|---|---|---|
| 设计 → 实现／视觉审查 | 批准设计依据、页面／状态清单、适用规范；设计稿或适用的运行入口及截图，标明产物类型、视口、状态、相关版本及数据是否mock | 设计任务的执行者完成或指派已批准的渲染步骤，不把可代办的截图工作交给用户 |
| 接口提供方 → 调用方／QA | 方法／路径、认证与归属、请求／响应、错误、精度／单位、适用幂等与状态语义；运行入口、可用状态及兼容约束 | 接口任务维护者补齐，调用方核对真实实现，不能只信文档 |
| QA／诊断 → 修复／复查 | 缺陷编号、预期来源、复现条件、实际结果、环境与版本、脱敏证据、关闭条件；诊断区分事实与假设 | 当前缺陷责任任务；修复者提供变更与回归证据，按质量卡安排复查 |

业务行为以批准需求为准，视觉以批准设计为准，接口契约须与需求及实现一致；截图是对应状态的证据，不是覆盖业务规则的新权威。相互冲突时说明影响并澄清，不凭文件修改时间、角色头衔或“最权威原型”自行裁决。

旧项目复用实际资料路径，不能要求PRD必须有某个固定章节号。已知进度从现有进度／运行记录读取；若某项输入确实缺失，应安排其产出或明确阻塞，不让下游等待无人负责的文件。

## 2. UI设计与交付模板

**触发：** 确有新设计或受影响界面。**输入：** 当前任务、批准需求、既有品牌／组件／设计、目标终端及状态清单。**退出：** 本任务所需设计确认、实际视觉证据及交接检查完成；正式界面还须满足对应行为验证。

```text
先检查现有实现和设计依据，复用可用部分；不默认暗黑、iOS风格、特定框架／图标库或图库。
根据使用者和核心任务，整理信息层级、组件规则、关键状态及目标尺寸，给出推荐方案。
新设计按任务许可制作代表页／必要原型，确认方向后再推广；普通小改沿用已确认方向。
由你准备适用的运行入口、可查看设计稿／真实渲染截图和对应版本／视口／状态，不等待用户提供本可生成的截图。
对照共用UQ要求实际查看页面／截图，记录具体差异，修正后复查；不以“截图已生成”代替审查。
保留权限、确认、校验和恢复行为；素材须合规，数据须脱敏，尊重已有本地／离线要求。
按交接约定提供设计依据、适用规范、页面状态清单、入口与截图、审查及未覆盖项。
```

质量细则只引用[UI审美与专业度](开发质量门禁与正确性验证标准.md#ui-quality)。设计稿、原型与正式页面分开标记；纯设计稿没有运行入口时如实说明，不能冒充软件可用。原型仅在任务需要时制作，正式界面仍必须实际渲染与验证；若缺浏览器或图像能力，按共用能力补齐流程处理。

<a id="implementation-task"></a>

## 3. 实现与集成模板

**触发：** 已批准的编码／联调任务。**输入：** 任务与质量卡、需求／设计、接口及现有工程映射。**退出：** 对应代码、适用验证与审查证据有效，下游所需契约和运行说明齐备。

```text
确认当前技术栈、锁定版本、目录、已有修改与批准范围；不另建默认工程或擅自升级到最新版。
先核对业务状态、接口和验收样例；新增或变化契约只维护项目指定的事实源，兼顾已有调用方。
契约至少说明本次涉及的认证／归属、输入输出、错误、数值精度与适用幂等规则，不强制固定OpenAPI版本。
在批准设计方向内先做通代表性的纵向闭环，再推广到其他页面／模块；不等全套UI做完才发现业务无法集成。
原有功能改造以受影响闭环回归为准，不为遵守模板重写已完成模块。
保留必要测试与服务端约束，按质量卡实际验证；原因不明或反复出现时再用根因诊断模板，不删断言掩盖问题。
交付实际变更、契约差异、启动／验证命令及结果、必要说明和未完成项，不仅交代码片段或方案。
```

纯接口／后端任务不强加UI步骤。设计样例、契约样例与测试预期须来自确认规则；测试预期不能直接复用被测计算逻辑。

<a id="qa-task"></a>

## 4. QA验证模板

**触发：** 计划时设计验证，代码可测后执行，修复后复查。**输入：** 需求与独立预期、质量卡、设计／契约、明确待测版本及环境许可。**退出：** 必需检查有真实结果、缺陷和未覆盖项可追踪，按共用门禁判断，不由测试报告替用户批准发布。

```text
先在计划阶段把本期验收项映射到正常／失败／边界用例，按风险选择平台和真实验证层次。
独立核对预期来源；每个用例有编号、前提、输入、步骤、预期、环境和对应需求。
执行前核对实际待测源码／依赖版本与数据目标，准备专用fixture及清理方案；旧成功报告不可复用冒充。
真实执行批准的检查，记录目录、命令、实际用例、失败／跳过和报告；未运行就是未运行。
UI验证实际页面及状态，图像与交互证据按共用标准；截图不能替代权限或事务检查。
缺陷包含复现、预期／实际、严重度、环境版本和脱敏证据；严重度与修复优先级分别说明。
修复后执行针对性回归并核对关闭条件，再做受影响回归；输出已证实结果、限制和下一步。
```

测试方案完成、测试执行完成、独立代码Review完成是不同事实。QA如修改了测试定义，应更新绑定证据并按职责安排审查；不能以“测试也是我写的”跳过独立预期核对或必需Review。

## 5. 根因诊断：事实 → 假设 → 实验 → 修复 → 复查

**触发：** 原因不明、证据相互矛盾或同一问题反复出现。**输入：** 缺陷、当前版本、复现条件、已尝试项及安全实验边界。默认先诊断；写代码仍须属于获准实现任务和单写入安排。

```text
先读取相关代码、配置项名称和必要脱敏日志，只询问现场无法取得的最小信息；不要求无删减秘密日志。
分开记录：已观察事实、待验证假设、已排除原因；说明每个判断的证据，不把推测写成根因。
选最有区分度的安全最小实验，明确预期、观察结果及对假设的支持／反证；避免同时改一堆无关变量。
未知写入先查证，生产／破坏性操作不用于随意复现；实验继承原任务权限与总预算。
证据支持后给最小修复；若仅有缓解办法或仍未证实原因，明确写出限制。
记录补丁只是建议还是已应用；应用后按共用红→绿规则和批准替代方案做针对性验证及回归。
交回缺陷编号、诊断结论及证据、实际改动、验证结果、未决项与精确下一步；达到无进展上限即安全交接。
```

**诊断完成不等于缺陷关闭。** 诊断意见可以交付，但缺陷仍须由获准实现任务修复并满足复查条件。不能因为解释合理就标“根治”；复现与替代证据规则引用[红→绿标准](开发质量门禁与正确性验证标准.md#red-green)，不另设豁免。

## 6. 本次吸收边界与后续验证

来源为用户提供的12份岗位提示词，主要提炼UI/UX、Backend／Web、Tester、Debug的专业职责和输入输出思路；未逐篇复制，原文件保持不变。使用本文不依赖外部提示词目录，也不要求先读全部12份。

未纳入：固定12-Agent编制、全套PM文档、固定工程路径／PRD章节、默认框架／主题／图库、强制最新版、固定模型或MCP安装清单。Flutter／Taro／Electron／浏览器扩展仅在项目确需该平台时另行适配；运维、反馈分析不成为本轮默认步骤，更不授予生产权限。

后续获准试点需实际观察：缺截图／版本冲突能否被交接检查发现；代表页能否同时满足视觉与业务；诊断建议未执行时缺陷是否仍保留；模板是否造成额外改栈或无关产物。比较需求遗漏、返工、人工介入和耗时，收益不足就精简，而不是追求更多角色。

**本次仅落盘模板与接入规则，未运行这些试点；文档检查不证明角色协作或编排器已经可用。**
