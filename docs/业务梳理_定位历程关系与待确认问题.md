## 1. 系统定位与边界

### 1.1 当前定位

按 `PRD.md` §1、§8 及 `Dev_Plan.md` §1.1、§7，系统是：

**供采购商（即采购方）使用、按加气站独立管理补货、销售、库存和往来记录的工具。**

本轮已确认的核心关系：

| 事项 | 已确认口径 |
|---|---|
| 主体与统一称谓 | 采购方就是采购商；本轮曾称“供应商”也指该采购商。统一使用“采购商”，不另设供应商主体 |
| 采购商与加气站 | 一个采购商对应多个加气站；沿用已确认的一个站点归属一个采购商 |
| 站点与库存 | 一站一独立库存，无公共或跨站共享库存 |
| 采购批次 | 每批采购只给某一个指定站点库存补货；批次用于记录补货和追溯 |
| 补货录入与确认 | H5 站点管理员按采购批次录入到货补货；本人确认弹窗提交成功后直接增加库存，无第二人审核或后台再确认 |
| 管理端分工 | 日常录入以站管端 `m-buyers.html` 原型为参考；后台也能调整，但主要用于查看、调整 |
| 消费者 | 系统不存在车队业务概念；车队人员也按散户下单、付款，从交易对应站点出气 |
| 当班与核销 | 一个站同一时间只能有一名当班加气员；加气前扫码核验，加气结束并确认实际量后完成核销 |
| 库存充足性校验 | 只在下单时校验，实际加气／核销不再因库存不足拦截 |
| 实际量与付款差额 | 本期不做线上差额处理，加不下或补加线下解决 |
| 退款边界 | 完成核销前可以退款，其他退款场景本期不考虑 |
| 数据录错 | 专项更正暂缓，后续再在后台增加修改功能 |

核心业务链为：

```text
站点管理员在本站采购批次下录入到货／补货
        ↓
本人核对确认弹窗并提交，无第二人审核
        ↓
保存成功后补充该站独立库存
        ↓
司机按散户在对应站点下单（校验库存）、支付
        ↓
本站唯一当班加气员在加气前扫码核验
        ↓
实际加气结束，确认实际量并完成核销
        ↓
只扣减本站库存，形成销售、收款及班次记录
        ↓
跟踪采购付款、票据、退款、对账和预警
```

系统要回答四类问题：

1. **买了多少**：在哪个站、采购什么气种、多少数量、什么价格、付了多少钱。
2. **还能卖多少**：已入库、已预占、已消耗、已调整及剩余可用数量。
3. **卖给了谁、交付了多少**：司机订单、优惠、支付、实际加气量、操作人及班次。
4. **钱和账是否对得上**：采购付款、销售收款、退款、渠道结算及票据跟进。

库存边界、入库操作人及确认方式均已明确：本站库存通过采购批次补货，站点管理员本人录入、自确认后提交生效，不经过其他人审批（Q02 已关闭）。“供应商”已确认就是此前的采购商，统一称“采购商”，Q13 已关闭，不新增业务主体。

### 1.2 明确不在当前范围内的事项

- 消费者电子钱包、充值、赠送金、余额支付或预付卡。
- 面向外部企业的开放平台、企业授信和挂账账户。
- 车队实体、车队账户、车队库存、车队专属结算；车队人员统一按散户交易。
- 采购商公共库存或跨站共享库存。
- 站点通用管理、枪机／设备管理及完整站务排班系统。
- 把预计气量当作实际计量凭证。
- 自动电子发票、全自动第三方财务对账等超出当前一期边界的能力。

本轮另明确暂缓：线上补款／差额退款、加气中的库存不足处置、完成核销后退款、录错数据的专项更正。加不下或补加线下处理，数据修改功能留待后续后台补充；这些不是本期需要继续完善的异常流程，不删除已有查看、库存调整和留痕能力。

旧版“天然气分销平台 PRD v0.9”已被当前 PRD 明确替代，不能把旧版账户、授信、开放平台等范围重新混入当前需求。

### 1.3 三种材料不能混为一谈

| 材料 | 用途 | 不能据此推断 |
|---|---|---|
| 需求与业务决策 | 确认经营规则、角色和范围 | 写入需求即代表已实现 |
| HTML 原型 | 演示页面和交互，保存在本地浏览器 | 演示支付、二维码和库存已接通真实服务 |
| Vue H5 与 RuoYi 后端 | 当前实现 | 已有代码即代表业务方确认，或已具备生产上线条件 |

当前范围以 `PRD.md` §8 的最新已确认答案为准；`Dev_Plan.md` §7.2 还包含方案默认做法，不能全部视为业务确认。最新简化答复覆盖旧的已完成后台退款、核销库存不足拦截和线上差额结算方案。

> 扫码时序已确认（Q03 关闭）：**加气前核验 → 实际加气 → 确认实际量 → 完成核销**。核验不等于完成核销，不在加气前执行实际量实扣；仍按“完成核销前可以退款”处理，不新增其他退款限制。

## 3. 各类关系

### 3.1 角色与主体关系

下表包含最新确认的业务职责；实际交付和权限差异见 §2.2。

| 名称 | 业务含义与职责 | 需要避免的混淆 |
|---|---|---|
| 采购商（即采购方） | 使用系统管理其对应站点的采购补货、销售、库存和资金记录 | 采购方与采购商是同一主体，不是两个上下游角色 |
| 采购商档案 | 采购商资料的系统表达，承载站点归属、收款商户、优惠成本和提醒对象等信息 | 是同一主体的数据记录，不是另一层经营主体；现方案不为每个档案单独开登录端 |
| 运营人员 | 维护基础资料和营销等业务；后台采购、库存以查看及调整为主 | 保留后台调整能力，不作为每笔站管补货的审核人；具体操作受权限控制 |
| 财务人员 | 登记采购付款、跟踪票据、查看相关账务 | 付款登记不是实际发起银行划款 |
| 站点管理员 | 在管理员端通过本站采购批次录入到货补货，本人确认弹窗后提交入库；处理本站管理及强制交班等事项 | 无第二人入库审核；本站入库写权限不自动扩大为跨站档案或商户配置修改权限 |
| 加气员 | 本站同一时间仅一名当班加气员核验、确认实际量并核销；现有代下单仍要求当班 | 不是替司机支付，也不能省略代下单的司机确认 |
| 消费者／司机 | 包括车队人员在内均按散户下单、付款、出示码、确认代下单、查询本人订单和券 | 不引入车队组织、车队库存或车队结算；会员身份不代表储值账户 |
| 拉卡拉、微信、短信服务 | 提供支付、身份／扫码、消息能力 | 外部通道成功与本地页面跳转成功不能混同 |

已明确“采购方”和本轮曾称的“供应商”均指同一采购商，后续统一使用“采购商”，必要时注明“即采购方”。当前后台账号组织与采购商档案的技术安排继续沿用原方案，不因统一称谓新增主体或独立登录端。

### 3.2 组织、账号与采购商的关系

当前确认模型如下：

```text
一套后台账号体系／经营管理团队
├─ 管理多个采购商档案（A、B……），不分别给采购商开登录端
├─ 运营、财务等按角色处理业务
└─ 站点部门
   ├─ 站点管理员
   └─ 加气员

采购商 A（采购方 A）
├─ 站点 A1 ── A1 独立库存 ← A1 的采购补货批次
└─ 站点 A2 ── A2 独立库存 ← A2 的采购补货批次
采购商 B（采购方 B）
└─ 站点 B1 ── B1 独立库存 ← B1 的采购补货批次
一个站点只关联一个采购商；各站仅从本站库存出气，互不共用
每站同一时间只有一名当班加气员核验、核销
所有司机（含车队人员）按散户交易，不关联车队库存
```

- 站点关联部门，员工的本站范围通过组织与站点关系确定。
- 采购商是业务归属维度，站点是现场操作和数据隔离维度。
- 当前采购批次和销售订单的采购商归属都来自站点，不是现场任意选择采购商。
- 采购商可以汇总查看其多个站点，但汇总视图不是共享库存；A1 站的补货不增加 A2 站库存，A1 站订单不扣 A2 站库存。旧原型中的多采购商库存表达仅作为历史记录，不再作为待选业务模型。

依据：`Dev_Plan.md` §1.1、§7；`GasPurchaseBatchServiceImpl.insertBatch`、`H5OrderServiceImpl.newOrder`。

### 3.3 主要业务对象关系

```text
采购商
├─ 收款商户配置（当前确认每采购商一个拉卡拉商户号）
├─ 优惠券模板／发放的券
└─ 多个站点
   ├─ 多把枪 ── 各枪价格历史
   ├─ 采购补货批次（只补本站，指定气种）
   │  ├─ 多次到货／入库记录
   │  ├─ 多次采购付款记录
   │  └─ 票据状态
   ├─ 本站唯一库存归属（现有实现按气种分项记账）
   │  └─ 入库、预占、释放、消耗、调整流水
   ├─ 销售订单
   │  ├─ 司机会员、枪号、下单价格与金额快照
   │  ├─ 最多一张优惠券
   │  ├─ 支付流水
   │  └─ 实际量、核销人、核销班次
   └─ 班次
      ├─ 代下单记录
      └─ 核销记录与交班汇总
```

几个容易混淆的关系：

- **采购批次是指定站点的补货记录**：不是另一份公共库存；以 `m-buyers.html` 的采购批次、分次进气为流程参考，站管录入本次到货补货后本人弹窗确认，提交成功增加库存。本轮不要求把采购批次与进气记录合并。
- **订单可扣本站多个批次，但不能跨站**：一笔核销可以在本站对应气种内跨多个到货批次按 FIFO 分摊。
- **下单员工不一定是核销员工**：订单分别记录代下单与完成时的员工／班次。
- **订单不等于支付流水**：订单业务状态与渠道支付事实需要分别记录，重复收款或关单后收款不能被简单抹掉。
- **预占量不等于实际交付量**：支付后占用可售数量，核销时才按确认量实际消耗。

### 3.4 气量、资金与账务关系

下表区分入库业务规则与退款方案。采购批次记录和本次实际进气记录仍分别表达；站管录入本次补货、本人确认并提交成功后增加库存，不增加他人审核步骤。当前页面和授权仍需按这一新职责分工补齐。

| 事项 | 气量变化 | 资金／记录变化 |
|---|---|---|
| 创建采购批次 | 不增加库存 | 记录采购数量、单价与应付金额 |
| 到货入库 | 站管录入、本人弹窗确认并提交成功后，增加本站该气种库存 | 不自动产生真实付款，也不等待后台审核 |
| 登记采购付款 | 不改变库存 | 记录付款并更新批次付款状态 |
| 创建未支付销售订单 | 最新要求先校验本站可用库存；仍不预占、不消耗库存 | 记录订单应付；选用优惠券时存在占券动作 |
| 司机支付成功 | 按预计量预占 | 记录销售收款事实 |
| 核销完成 | 仍记录确认量、本站消耗及预占释放；最新要求不以库存不足阻断，现代码尚需调整 | 不处理实际量与付款的差额，加不下或补加线下解决 |
| 库存调整 | 指定到货批次增减，填写原因 | 不等同于退款或采购付款 |
| 完成核销前退款 | 按退款结果释放预占 | 本期保留此范围，真实退款闭环仍待实现 |
| 已完成退款（本期暂缓） | 本轮不新增处理流程 | 原后台部分／全额退款方案暂缓，不据旧方案继续扩展本期范围 |

当前数量口径：

```text
预计气量／预占量 = 原价金额 ÷ 下单时枪价
司机实付金额     = 原价金额 − 优惠金额
实际库存扣减量   = 加气员确认量
可用库存         = 累计入库 + 净调整 − 已消耗 − 已预占
```

一站一库存是业务归属边界；现有实现仍在本站库存内对 CNG（m³）与 LNG（kg）分项记账，不能直接相加，也不因此产生公共库存。最新库存量门槛仅在下单时校验，不移到实际加气／核销；当前预占与核销算法仍需衔接新规则，见 Q05。

- `h5/`：实际 Vue/Vant 前端，当前主要是消费者和员工流程。

## 4. 当前主流程

### 4.1 采购与库存

```text
站点管理员进入管理员端（原型 m-buyers.html）
→ 维护本站采购批次，录入本次到货／补货数量
→ 显示确认弹窗，由同一名操作人核对
→ 确认并提交成功，生成入库记录及操作留痕
→ 只增加本站对应气种库存
→ 本站销售核销按本站到货先后消耗
→ 根据余量产生补货／票据提醒

后台：以查看批次、库存、流水和调整为主，不承担每笔入库审核。
```

确认弹窗是防误操作，不是第二人审批；取消确认不增加库存，提交失败不应显示入库成功。原型现有进气录入弹层提交后直接写入，后续需补充录入完成后的复核弹窗；本轮只记录需求，不改原型或实现代码。

采购付款、票据维护是并行的管理动作，不要求先完成付款登记才能入库。库存调整需要批次和原因，不应把调整当作掩盖销售差异的替代操作。

初次梳理时后端允许超采购量到货并仅记录告警，管理员原型则拒绝超量。用户已确认方案 A：同批次累计到货不得超过采购数量，超出部分另建批次。M1 首轮已将共享入库服务改为拒绝超量，并保护采购数量不得缩至累计到货以下；尚待隔离库事务／并发验收，见 Q09 及 `docs/模块开发进度.md`。

### 4.2 司机主动下单

```text
扫描站点码／进入对应站点
→ 完成需要的身份授权与手机号绑定
→ 选择枪号，输入原价金额
→ 试算单价、预计量和可用券
→ 下单时校验本站可用库存足够（新要求，现实现待补齐）
→ 创建待支付订单
→ 发起支付
→ 服务端确认支付事实
→ 订单待核销、预占库存
→ 本站当班加气员在加气前扫码核验订单
→ 实际加气
→ 加气结束，确认实际量并完成核销
→ 完成订单，记录本站库存消耗
```

当前实现的主要状态：

```text
待支付（WAIT_PAY） ──支付成功──→ 待核销（PAID） ──核销──→ 已完成（COMPLETED）
      └──────────超时────────→ 已关闭（CLOSED）
```

- 订单保存下单时枪价和金额，不是核销时重新按最新价计算。
- 支付事实与库存预占采用分开的事务处理；预占失败会留异常说明，不能把已收款事实回滚掉。
- “待核销”并不能证明现场尚未开始加气，当前没有单独的“加气中”状态。
- 当前核销页把预计量预填为实际量；实际确认量的原记录口径不变，本期不处理它与付款的资金差额。
- 实际加气／核销不应因库存不足被拦截；现有代码仍有此拦截，需要后续修改。核销的身份、站点、订单状态和重复操作校验仍保留。
- 已确认加气前扫码核验；核验只用于核对订单，不立即完成核销或按实际量实扣。加气结束确认实际量后再完成核销，不因此新增退款门槛。

### 4.3 加气员代下单

```text
员工开始当班
→ 扫司机会员码
→ 选择枪号、填写金额
→ 下单时校验本站可用库存足够（新要求）
→ 创建待司机确认订单
→ 司机核对、选择优惠券、确认
→ 待支付
→ 支付成功
→ 进入与主动下单相同的核销流程
```

司机确认前不收款、不预占。拒绝或确认超时关闭订单；当前代码将拒绝记录为 `CLOSED` 并注明原因，方案早期状态图中的 `REJECTED` 不应直接当作现有状态。

### 4.4 当班、交班与责任归属

```text
开始当班 → 代下单／核销 → 结束当班 → 固化班次汇总
                          └→ 必要时由站管填写原因强制交班
```

- 当前已确认且已实现：同站同时一人当班，非当班人不能操作代下单／核销。
- 未完成订单不随交班关闭。
- 代下单数按创建班次统计；核销数、CNG/LNG 实际量和金额按完成班次统计。
- 当前班次金额是该班完成订单的 `pay_amount` 合计，不是“该班期间支付渠道实际到账金额”。

因此，跨班支付、跨日核销及核销前退款的经营报表，仍应区分时间和归属口径，不能直接拿班次金额代替渠道对账；完成核销后退款不纳入本期流程。

### 4.5 退款、差额和纠错：本轮简化范围

- **退款以完成核销为界**：完成核销前可以退款，不需要审批，不另加“已经开始加气不可退款”的业务门槛；其他退款情况本期不考虑。原已完成订单后台退款方案暂缓。
- 核销前全额原路退款、释放预占、有效券退回仍是现有方案细化；真实退款尚未实现。退款后的订单不能再核销，重复退款保护继续保留。
- **实际量与付款差额不在线上处理**：加不下、少加或补加线下解决，不新增线上补款、按实际量重算应付或部分差额退款。
- **录错数据的专项更正暂缓**：后续再增加后台修改功能，不在本轮定义完整纠错流程；不删除现有正常查看、库存调整与留痕能力。

现有支付异常记录、幂等和状态保护仍保留，不因业务范围简化而删除；记录异常不等于已完成真实渠道退款或补偿。本轮不把其他特殊情况继续扩展为必须先做完的异常流程。
