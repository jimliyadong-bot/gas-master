## 3. 四项关键技术方案（建议，待确认）

### T1：实际量不足库存时，完整记账而不是拒绝核销

**建议采用“完整消耗 + 显式待分摊记录”的方案。** 这是新增账务语义及数据结构建议，须在 M2 前批准，当前未执行。

1. 完成订单时，按实际量完整增加本站库存消耗并结束本单预占；账面余量必要时允许为负，不借用其他站库存。
2. 当时有余量的到货记录仍按本站、同气种、到货 FIFO 分摊。
3. 不足的部分记录为该订单的“待分摊消耗”，保留订单、站点、气种、数量、完成时间和操作人；不伪造到货、不少记消耗。
4. 后续真实补货先正常记入库；建议按消耗发生先后补齐待分摊数量。补分摊只补批次对应关系，不再次增加总消耗、不再次扣库存，明确标识为后补账务分摊，不伪装成核销当时已有该批到货。
5. 消耗事实与批次分摊应可分别重算：订单实际消耗 = 已分摊量 + 待分摊量；站点账面余量 = 各到货记录剩余量合计 − 待分摊量，可用量再减有效预占。
6. 后台展示账面不足／待分摊及追溯记录；后续补货不能静默改写历史消耗事实。

**迁移影响**：预计新增消耗分摊／待分摊结构及唯一约束；已有 CONSUME 流水只用于建立已有分摊对应关系，不再次累计池余额。实施前细化表结构、旧流水映射、锁顺序、回算校验及迁移步骤。库存调整、批次余量提醒和查询也需使用一致口径；不直接删除现有调整保护或补造余额。

### T2：下单检查与支付后预占分开

- 主动下单、代下单共用本站气种可用量检查，预计量按原价金额／下单枪价计算。
- 创建未支付订单不预占。两个未支付订单可能都通过检查；不能把下单校验宣称为全程库存保证。
- 支付事实与库存预占保持可恢复、可追溯，重复回调只能产生一次有效预占；不能在收款后通过新增“库存不足”拒绝来绕开已确认流程。
- 订单锁、预占及 M4 退款释放的锁顺序一起设计，覆盖“支付事实已提交但预占尚未完成时退款”的竞态，不能退款后又被迟到预占重新占库存。
- 预占失败不能抹掉真实收款；保留异常记录，并明确重试／恢复路径。付款失败与未支付超时不产生预占。

### T3：短期动态码换取服务端核验上下文

**建议新增服务端核验记录，不延长原动态码，也不在核验时提前完成订单。**

- 有效扫码后原子兑换核验上下文，绑定订单、站点、核验人、本人班次；码的重复使用和核验请求重试要有明确的幂等语义。
- 核验只记录核对结果，不改变订单为完成，不执行实际量扣减，也不新增“加气中”业务状态。
- 加气结束提交核验凭据与实际量；服务端重新校验账号／角色／绑定、本站、本人班次、订单状态及上下文状态，不再要求原动态码仍有效。
- 上下文采用有限、可配置有效期；具体时长、刷新页面后的恢复、超时重新核验策略在 M3 前定稿，不默认为永久有效。
- 交班、退款申请／成功、关闭或核销完成后旧上下文不可继续使用；下一班处理未完成订单需要重新核验，不继承上一班凭据。
- 原动态码仍按 30 秒刷新、60 秒有效、单次使用；核对新码生成与旧码失效策略。两个司机码页面改为真实二维码，不把 token 文本当扫码成品。

### T4：核销前退款状态机及渠道结果

**建议先完成 mock 可验证退款契约，再实现真实拉卡拉适配。**

- 退款与核销竞争同一订单的状态控制：未完成且已付款的订单方可进入退款处理中；已完成服务端拒绝。
- 退款开始即阻止继续核销并使旧核验凭据失效，不增加现场“开始加气后不可退”的门槛。
- 渠道调用在数据库长事务外执行；持久化退款业务号、请求及结果，支持请求重试、查单补偿、回调幂等。
- 只有确认退款成功，才按幂等规则完成预占释放、相关券处理和退款成功记录。
- 渠道超时／结果未知仍为处理中，不恢复可核销、不显示成功；明确失败后如何恢复待核销／允许重试要在状态机中列明，旧上下文不能自动复活。
- 退款与支付预占、重复支付通知及重复退款通知共同做竞态测试。真实支付异常记录继续保留，但本模块不扩展为已完成退款或其他特殊退款业务。

### M1：H5 站管采购补货——第一个业务开发模块

分步执行：

1. 增加站管身份入口、本站批次／补货／库存查询接口；强制服务端身份与本站范围。
2. 增加本站采购批次创建／查看、批次下补货录入；付款、票据、跨站档案和商户编辑不顺带开放。
3. 实现“录入 → 本人确认弹窗 → 提交 → 库存刷新”，取消不写入，失败保持可重试。
4. 为批次创建及补货提交设计服务端请求幂等：同请求同内容返回原结果，改参数复用请求号应拒绝；到货记录、池增加、流水在同一事务内完成。
5. 核对既有站管角色并补集成测试，再做浏览器取消、失败、重复点击、刷新与重试检查；现有角色已满足 H5 补货，无需额外开放后台写权限。

**文件范围**：

- `h5/src/router/index.js`、`h5/src/api/station.js`、身份入口页面；新增站管页面、提交凭据工具与测试。

- `RuoYi/ruoyi-gas/src/main/java/com/ruoyi/gas/service/impl/`：复用采购批次、到货、库存及站管身份服务；新增必要 DTO／服务及 Mapper。
- 已新增 `RuoYi/sql/gas_m1_station_refill_upgrade.sql`：只创建 `gas_station_write_request` 幂等表，不改历史数据、不额外开放后台写权限，尚未执行。请求键为站点＋用户＋操作＋请求号，并校验载荷指纹。

### M2：下单库存检查与实际消耗记账

1. 共用库存校验，覆盖主动／代下单；保留支付后预占。
2. 按批准的 T1 方案完整记录实际量，取消核销时的库存量阻断，不取消身份、站点、状态保护。
3. 完成 FIFO、待分摊、补货后分摊、流水回算及调整／提醒口径衔接。
4. 细化与支付、退款衔接的锁顺序和幂等；迁移在确认目标及备份方案后执行。
5. 修改与旧规则冲突的测试，保留其他库存隔离、事务、重放保护测试。

**文件范围**：`H5OrderServiceImpl.java`、`H5StaffServiceImpl.java`、`InventoryServiceImpl.java`、相关库存／订单 Mapper、M1 补货衔接、现有库存／订单／员工测试；拟新增 `RuoYi/sql/gas_m2_inventory_accounting_upgrade.sql`。

**完成标准**：库存足够／刚好／不足下单；用券不减少预计量；已支付并发预占；实际量超过预计量或可分摊量仍正确完成；站点互不借库；订单、池、批次和账本可核对，补货不重复记消耗。

### M3：加气前核验、加气后核销及二维码

1. 新增核验上下文与完成接口，按 T3 处理过期、刷新恢复、重试及交班失效。
2. 员工页面明确区分“核对订单”和“确认实际量完成核销”，完成前必须人工核对实际量，不把预计量当实测值。
3. 司机会员码和订单核销码生成真实二维码；核对微信扫一扫输入／输出及动态码刷新。
4. 保留一站一当班人、跨站／非当班拒绝、重放保护；完成订单详情显示实际量和完成结果。

**文件范围**：`h5/src/views/StaffRedeem.vue`、`OrderDetail.vue`、`MemberToken.vue`、`h5/src/api/scan.js`；员工服务、核验 Domain／Mapper、动态码 Mapper、员工接口及测试；拟新增 `RuoYi/sql/gas_m3_inspection_upgrade.sql`。

**完成标准**：核验不扣实际库存；已合法核验后跨过原码有效期仍能按方案完成；过期未核验码拒绝；重复完成无副作用；交班或状态变化使旧凭据失效。退款联动在 M4 再回归；微信真机证据不足时单独标记未验收。

### M4：核销前退款与券状态

1. 新增退款领域、持久化状态及渠道退款／查询契约；检查现有预建退款表是否可复用，不能因有表就认为功能已有。
2. mock 支持成功、明确失败、处理中／超时及重复结果，先验收状态链。
3. 司机订单详情增加适用订单的退款入口和处理中／失败提示；完成订单无入口，服务端同步拒绝。
4. 退款成功只释放一次预占、按确认规则处理券并留日志；撤销旧核验凭据。
5. 测退款与核销、退款与迟到预占、请求／回调重放；真实通道另在 M6 接入验收。

**文件范围**：`h5/src/views/OrderDetail.vue`、H5 订单／退款接口与服务、`IPayGateway.java`、`MockPayGateway.java`、券及库存服务、退款 Mapper；拟新增 `RuoYi/sql/gas_m4_refund_upgrade.sql` 和 `GasRefundServiceTest`。

**完成标准**：只处理核销前全额退款；退款和核销仅一方成功；渠道结果未知不伪装成功；重复请求不重复退钱／退券／释放库存。后台退款操作入口如沿用默认方案，仍限定相同范围与权限，无审批。

### M5：补齐必要查询、角色权限和业务文案

按子步骤分轮，不扩大为全套财务系统：

1. 后台销售订单列表／详情、付款与退款结果、核验与完成信息、库存／待分摊追溯；补必要筛选及导出。

3. 采购、到货、库存调整及提醒记录权限对齐；不删除已有调整留痕，也不扩展任意修改历史原单。
4. 查看／导出同样做本站隔离。文案区分预计／实际、原价／优惠／实付／退款、核验／完成。
5. 按明确口径提供必要统计；支付日、完成日分别表达，班次金额不冒充渠道到账。复杂经营大屏、全自动对账不作为隐含任务。

## 5. 验证计划与命令

### 前置条件

- H5 编译需要 Node/npm 及依赖；真实页面验收还需后端和相应测试数据。
- 后端业务测试是会写 MySQL 的集成测试，不是内存单元测试。**仅在用户确认的本地隔离测试库运行**；不读取或在会话展示密码／密钥。
- 升级脚本按模块新增，先核对目标与备份；`RuoYi/sql/gas_schema.sql` 含删表，不能当存量升级脚本。

### 已有命令

在 `h5/`：

```sh
npm run build
```

在 `RuoYi/`，只编译打包（含测试编译，不执行测试）：

```sh
mvn -pl ruoyi-admin -am -DskipTests package
```

确认隔离库后，按模块选择现有回归：

```sh
mvn -pl ruoyi-admin -am -Dtest=GasInventoryServiceTest -Dsurefire.failIfNoSpecifiedTests=false test
mvn -pl ruoyi-admin -am -Dtest=GasOrderServiceTest -Dsurefire.failIfNoSpecifiedTests=false test
mvn -pl ruoyi-admin -am -Dtest=GasStaffServiceTest -Dsurefire.failIfNoSpecifiedTests=false test
mvn -pl ruoyi-admin -am -Dtest=GasH5AuthFlowTest -Dsurefire.failIfNoSpecifiedTests=false test
```

M1 不连库单元测试已创建，可单独执行：

```sh
mvn -pl ruoyi-admin -am -Dtest=GasStationRefillUnitTest -Dsurefire.failIfNoSpecifiedTests=false test
```

M1 数据库测试已创建，但以下命令**只在确认隔离库、执行增量 SQL 并获准写入后运行**（Bash）：

```sh
GAS_ALLOW_DB_TESTS=true mvn -pl ruoyi-admin -am -Dtest=GasH5StationRefillTest -Dsurefire.failIfNoSpecifiedTests=false test
```

`GasRefundServiceTest` 仍未创建，不得提前选择它并以零用例宣称通过。

M5 查询测试具体类名在该模块编码前补充。全量后端回归命令为 `mvn clean package`，同样会写测试库，需满足相同安全前提。
