# 加气项目：手动SOP使用过程样例

> 版本：v1.0｜日期：2026-11-21｜依据：手动SOP v1.4、共用质量标准 Q-v1.1、专业任务模板 T-v1.0。
>
> **这是使用过程的教学样例，不是执行记录或授权文件。** 本轮只编写文档，未修改业务代码、未运行项目测试、未执行SQL、未安装工作流资源或启动额外Agent。
>
> 下文“你发送”“AI应交付”描述将来实际使用时的对话。示例确认语句不代表用户现在已经确认，所有`演示-`编号都不是已建立的真实任务；`【括号】`须替换为届时实际内容，不空着照抄。

对应手册：[通用项目流水线开发SOP](通用项目流水线开发SOP.md)。另一条可选路径见[自动SOP使用过程样例](加气项目_自动SOP使用过程样例.md)。**两份是二选一的操作方式，不是把同一模块重复开发两遍。**

## 0. 这个样例讲什么，真实项目到哪了

用同一条业务主线演示：**接入已有加气项目 → 处理M1保留验收项 → 梳理M2下单库存校验与核销记账 → 审核计划 → 逐任务开发验证 → 验收与交接**。

### 真实起点：2026-11-21文档快照

| 事项 | 当前记录，不是本样例执行结果 |
|---|---|
| 工程 | 根目录`D:/Project/workspace/gas`；`h5/`是Vue/Vant，`RuoYi/`是嵌套Git仓库和Java17后端，后台页面为Thymeleaf |
| M0 | 顺序、方案A、保留Java17已确认，不重走Java8迁移 |
| M1 | 实现待验证（核心自动化通过，待验收收口）；已有62项历史通过记录，不是本轮重跑 |
| M1保留项 | 后台实际登录／Thymeleaf对账、用户流程确认及尚未组合验证的异常场景 |
| M2 | 待开始；T1不足库存时如何完整记账、T2支付预占并发／恢复方案仍需确认 |
| 工作流 | 快捷命令和自动编排器尚未完成安装验收；本例用自然语言，不依赖`/flow-next` |

实际使用时重新读取[项目规范](../AGENTS.md) → [新会话交接](新会话开发交接.md) → [模块进度](模块开发进度.md)。业务以[PRD §8](PRD.md)和[开发方案 §7](Dev_Plan.md)为准；[分模块计划](分模块开发实施计划.md)用于定位方案与依赖，旧段落中的状态不能覆盖最新进度。

原型`design/prototypes/`不是实际H5。旧工作区修改必须保留；不因写样例创建第二份PRD或实际运行状态。本文不是项目进度事实源。

## 1. 第一步：进入项目，让AI接上现有进度

**对应手动SOP §3。** 在项目根目录打开Pi。把SOP路径告诉AI即可，不必把整个项目资料重新粘贴一遍。

**你发送：**

```text
请按docs/通用项目流水线开发SOP.md接入当前加气项目。
先读取AGENTS.md、docs/新会话开发交接.md、docs/模块开发进度.md，
再按当前任务读取PRD、开发方案及分模块计划。
先只读核对：现在完成到哪、下一步是什么、哪些只是历史记录或待确认方案。
保留Java17、现有Vue/Vant与Thymeleaf，不重做已完成模块，不清理已有修改。
本步不编码、不跑项目测试、不执行SQL、不安装资源。请给简短接入结论。
```

**AI应交付的样子：**

> 若现场仍与本例快照一致：M1不能直接标已验收；下一步先处理保留项。M2可以梳理方案，但T1/T2未确认，不能开始其实现。已有文档可复用，无需重新生成整套需求资料。

**你检查：** 工作目录和项目是否正确；有没有把“核心自动化通过”说成“整个项目完成”；有没有又要求确认Java版本或重新导入初始化SQL。

## 2. 第二步：先交代M1尾项，不跳过前置依赖

**对应手动SOP §7—§8。** 这一步不是重新开发M1，而是决定怎样收口。

**你发送：**

```text
请根据M1的真实验收记录，列出仍需完成的检查、所需环境和证据。
区分只需补验证、发现缺陷才需修复、需要我实际使用确认的事项。
说明这些保留项对M2的影响，不把历史通过数量当成本次验证。
先给收口计划，不直接开始M2或运行尚未明确范围的操作。
```

**AI应交付：** 保留事项清单、具体检查方法、是否需要修复任务、影响M2的依赖条件。历史证据入口为[M1验收步骤与测试](M1_站管采购补货_验收步骤与测试.md) §10。

将来确需执行补测或修复时，也按本例第5—7步的“明确范围→批准→执行→验证”小循环处理，不能因一句“收口”随意改代码。

**将来确已完成后，你才发送验收确认，例如：**

```text
依据【实际M1证据包】，确认【明确验收范围】。
仍保留【实际未完成项／无】，按已核对的依赖结论进入M2方案阶段。
不要把部分确认扩大为整模块验收，也不要自动开始M2编码。
```

**本例后续情境前提：** M1的相关依赖已在将来按证据满足并记录。本文件不表示这件事现在已经发生；必要依赖未满足时，不能照着后文越过它。

## 3. 第三步：用业务语言打磨M2，不重问已确认规则

**对应手动SOP §4。** 你不必重新写PRD，直接说明本次想解决什么。

**你发送：**

```text
我准备推进M2：主动下单和加气员代下单都要检查本站对应气种的可用库存。
继续保持支付成功后预占，按原价金额除以枪价计算，不按优惠后的实付计算。
实际加气后按确认量完整记账，不能因库存不足拒绝核销；身份、本站、当班和状态保护不变。
请沿用已有PRD，不恢复钱包、充值、车队、共享库存、补货审批或线上差额结算。
本次不提前实现M3核验上下文、M4退款和真实渠道接入。
先给需求范围、验收样例与技术待定项，不编码。
```

**AI应交付：** 已确认业务规则、需要设计的T1/T2、当前范围的验收样例，而不是把T1的建议自动写成“用户已选择”。

以下是**合成验收样例，未创建订单或写入数据库**；均假定其他下单条件满足：

| 场景 | 可观察预期 |
|---|---|
| CNG原价400元，枪价4元/m³，用券40元，实付360元 | 预计量100.00 m³，不是90.00 m³ |
| 本站CNG可用99.99 m³，订单预计100.00 m³ | 库存不足不能下单；别站有库存也不能借用 |
| 本站可用刚好100.00 m³，其他条件满足 | 通过库存检查；创建未支付订单不产生预占 |
| 同一支付成功通知重复到达 | 只产生一次有效预占；具体恢复机制待T2定稿 |
| 实际确认105.00 m³，届时可分摊量不足 | 不因库存不足阻断，完整记录105.00 m³；账务实现由批准后的T1确定 |

CNG/m³与LNG/kg必须分别验证，不能相加。并发未支付订单都通过一次检查，不等于后续库存永远充足。M1方案A仍要求累计到货不超过采购量，销售消耗不恢复该批次的补货额度；核销不因库存不足阻断，不等于允许超量入库。

**你核对理解后发送：**

```text
上述业务理解与既有确认一致，请记录本次M2范围及验收依据。
T1/T2仍进入技术方案评审，不把建议当批准；本步只进入计划梳理。
```

## 4. 第四步：看方案、拆任务、微调顺序

**对应手动SOP §5—§6。**

**你发送：**

```text
请结合现有实现给出T1/T2的方案、影响、替代选择及需要我决定的事项。
特别说明完整消耗、FIFO追溯、后续补货、支付幂等与失败恢复怎样衔接。
若涉及新表或迁移，分开列脚本编写、隔离演练和实际执行，不沿用测试许可直接执行迁移。
然后按依赖拆M2任务，附质量卡、实际候选文件、测试与Review安排、UI影响和交接产物。
先自查；需要独立Review时说明方式与权限，未获准不要启动额外Agent。
```

**可能的计划形状，仅为拆分演示：**

| 教学编号 | 交付目标 | 前置条件／验证重点 |
|---|---|---|
| 演示-M2-A | 主动／代下单库存检查 | T2相关规则明确；足够、刚好、不足、优惠及本站隔离 |
| 演示-M2-B | 支付预占幂等与恢复 | T2批准；与A联调；重复通知和异常可恢复 |
| 演示-M2-C | 按实际量完整记账 | T1批准；B相关契约；不足不阻断、状态保护及账本一致 |
| 演示-M2-D | 补货与消耗追溯衔接 | T1批准；C；若采用待分摊方案，补分摊不能重复记消耗 |
| 演示-M2-E | 受影响H5提示／展示与交互 | A—D相关契约稳定；复用既有设计，实际预览和功能回归 |
| 演示-M2-F | 集成、回算与模块交付 | 前面适用任务满足退出条件；核对M1补货兼容及未完成项 |

这些不是已下发任务，也不是完整工程方案。真实拆分须明确结构／迁移准备、锁顺序、库存调整和提醒口径等必要子步骤，不能因表格简短漏掉它们。

**你可以这样微调：**

```text
我想先看到主动下单与代下单的库存检查闭环。
请先细化这个小任务，但不要删掉支付、记账和补货衔接的后续依赖。
暂不做无关页面改造。请检查调整后的风险和依赖，再给我具体计划版本。
```

AI应先在[现有设计规范](../design/specs/Design_Spec.md)内处理代表页面与状态，而不是换Next.js、重做15页或把全部UI做完才联调。涉及库存、隔离与幂等，质量卡通常为L2，按[共用标准](开发质量门禁与正确性验证标准.md)选择真实验证与独立审查。

**进入下一步的条件：** 当前任务所依赖的T1/T2内容已真实确认，计划和质量卡经过所需审查，M1依赖及环境可满足。当前项目尚未因本样例获得这些确认。

## 5. 第五步：批准一个明确任务，不批准“随便做”

**对应手动SOP §6.2、§7.2。** AI先给任务卡，你只需核对并确认实际版本，不手写整套配置。

**你应看到的任务卡重点：**

- 目标、对应需求、真实任务编号与计划版本；不能直接把教学编号当真实批准。
- 允许修改的文件白名单：服务／Mapper在`RuoYi/ruoyi-gas/`，HTTP控制器及业务集成测试在`RuoYi/ruoyi-admin/`，实际前端在`h5/`；这些目录只是定位，不等于整目录可任意修改。
- 必需测试、工作目录、预期来源、独立Review方式、UI适用项，以及证据和交接责任。
- 本地库既有许可目标为`127.0.0.1:3306/ry`；未来实际执行时核对目标，同目标同范围不重复询问。仅专用fixture与回滚／按ID清理，不含新迁移、清空整表、重置自增或重跑`gas_schema.sql`。
- 必要工具的复用／安装策略和预算；普通准备许可不包括付费、提权、新凭据、私有数据外传或更换模型供应商。

**仅在真实核对完成后，你发送：**

```text
确认我刚审阅的计划【实际版本／摘要】及当前任务所依赖的技术决策【实际编号／版本】。
本轮批准【一个真实任务编号】，按执行卡【实际编号】中的文件、验证、Review、权限和预算执行。
必要免费本地工具按卡片策略自行补齐、加载并验证可用。
数据库沿用仍适用的已记录许可，新增迁移等超出范围的操作另行确认。
不提前实施其他模块，不提交Git、不发布、不改框架或配置来绕过测试。
```

也可批准明确的一组任务，然后每轮手动触发其中一个；同一批准不反复重签。但只批准一个时，不能顺带执行剩余任务。

## 6. 第六步：让AI完成一个任务的小循环

**对应手动SOP §7；专业方法见[任务模板与交接约定](专业任务模板与交接约定.md)。**

**你发送：**

```text
请继续当前已批准任务，先核对现场和上游产物版本。
完成范围内实现、必要测试与审查；普通缺陷在原许可和预算内修复、重测，不必每改一行问我。
受影响界面沿用现有蓝白主题、本地组件与SVG，实际查看页面／截图并验证交互。
保存真实变更、证据、遗留项和下一步。本轮不越过任务边界。
```

**AI应做的过程：** 核对任务与权限 → 准备能力 → 实现一个闭环 → 测试 → 所需独立Review → 修复和复查 → 保存结果。

例如下单服务交给前端／QA时，应交付库存不足的实际错误契约、相关源码版本、运行与验证入口；前端交付对应页面状态和截图，标明视口、版本及是否mock。用户不必手工搬运这些产物。

**你检查结果，而不是只看“已完成”：**

| 验证边界 | 应看到什么 |
|---|---|
| 后端 | 在`RuoYi/`执行的具体命令、实际JUnit用例／失败／跳过数量，及当前版本报告 |
| 数据与HTTP | 实际目标、专用数据、隔离／事务／幂等证据和清理结果；mock支付不是实际渠道收款 |
| H5 | 在`h5/`进行的构建、受影响页面／状态的实际浏览与交互、视觉审查结果；不能凭构建通过替代后端或UI验收 |
| 审查与交接 | 审查范围、版本、发现和复查；同一会话自查不能冒充独立Review |

本文不预填测试命令的实际结果、通过数量或截图位置；这些必须由当轮执行产生。

## 7. 第七步：遇到失败，怎样继续而不是重来

**对应手动SOP §7.4、§11。** 假设将来测试发现：本站只有99.99 m³，但400元原价、4元枪价的订单用了券后仍被允许创建。**这是教学假设，不是本轮发现的缺陷。**

**你可以发送：**

```text
请围绕这个具体失败保留复现，不要清库、重做项目或直接删除断言。
核对预期量是否按原价计算，区分已观察事实与根因假设，用最小安全实验取证。
在当前批准范围内修复，重跑针对用例及主动／代下单、隔离和相关回归，再复查。
若必须改变方案、增加迁移或扩大权限，先说明最小决策点，不自行越过。
```

AI不应仅凭现象就断定“肯定取了实付金额”。它应提供事实→假设→实验→实际修复→复查证据；不能把给出补丁建议当成已经修好。

缺工具时在已有许可内补齐；真正缺权限、环境不可得、预算耗尽或写入结果未知时，保存阻塞及精确恢复动作。缺环境不能写为`NOT_APPLICABLE`，失败不能改成`PASS`。

## 8. 第八步：核对证据，决定验收与下一任务

**对应手动SOP §8、§12。**

**你发送：**

```text
请对照本次实际批准范围和质量卡给出验收摘要：
需求对应哪些实现、测试和审查证据，哪些未测、失败或仍阻塞。
如只做完一个子任务，不要把整个M2标成完成。
核对需要重跑的受影响回归、测试数据清理和是否存在未知副作用。
请给我实际使用检查路径，不用“全部正常”代替证据。
```

AI应按`PASS／FAIL／NOT_RUN／BLOCKED／NOT_APPLICABLE`记录适用检查，实际用例数、报告和源码版本可核对。库存不足、用券预计量、主动／代下单、跨站与重复操作等以质量卡为准，不用本例五个样例替代全部必需检查。

**将来实际验收后，你才发送：**

```text
依据【实际证据包与使用检查】，确认【实际验收范围】。
保留【未完成项／无】，不要扩大验收结论。
若还有已批准且依赖满足的M2任务，请给出下一任务；本次仍按手动方式逐任务推进。
M2整模块完成后，先整理M3及T3方案，不自动开始其实现或上线。
```

若只通过子任务，其余M2仍待完成；若必需检查失败，先回到第7步。模块业务验收、真实支付／退款／微信真机／短信验收和生产发布是不同结论。

## 9. 随时插入的操作：保存、换会话、暂停或改需求

**对应手动SOP §6、§9、§11。**

**换会话前，你发送：**

```text
请暂停新增实现，保存实际进度、批准版本、已验证证据和未完成项。
复用docs/模块开发进度.md及docs/新会话开发交接.md；若已有独立状态入口，给出其真实路径。
记录当前任务、已有修改、未知写入、尚在运行的本轮进程和下一条精确动作。
写前复读，保存后核对；不要只说“已经记住”，不要把本教学样例当成实际检查点。
```

等保存完成后，在同一项目目录新建会话；不要用携带旧历史的继续／克隆操作冒充精简文件交接。

**新会话，你发送：**
