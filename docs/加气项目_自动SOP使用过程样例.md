# 加气项目：自动SOP使用过程样例

> 版本：v1.0｜日期：2026-11-21｜依据：自动SOP v1.3、共用质量标准 Q-v1.1、专业任务模板 T-v1.0。
>
> **这是使用过程的教学样例，不是执行记录或授权文件。** 本轮只编写文档，未修改业务代码、未运行项目测试、未执行SQL、未安装工作流资源或启动额外Agent。
>
> **当前编排器尚未完成实现、安装和运行验收。** 下文自动执行、独立角色调度、自动换会话和控制命令，都是将来具备并验收能力后的使用情境，不能据此声称现在已经可用。

对应手册：[通用自动开发流水线SOP](通用自动开发流水线SOP.md)。现在需要实际逐步操作时，可参考[手动SOP使用过程样例](加气项目_手动SOP使用过程样例.md)。两份是替代路径，不应把同一模块重新开发两遍。

所有`演示-`编号和状态输出均为教学示意，不是已创建的任务或run；`【括号】`须替换为届时真实内容。示例中的确认句不构成当前授权，不写入真实批准事件或任务状态。

## 0. 整段过程先看一遍

```text
接入加气项目，核对工作流能力与M1依赖
→ G1：确认M2业务范围与验收依据
→ 设计T1/T2、拆任务、独立计划Review、微调
→ G2：确认计划
→ G3：确认角色、文件、验证、能力准备、数据目标和有限预算
→ 经实际入口启动：实现→测试→独立Review→修复→复查→证据核对
→ 同一批准批次内自动接下一任务，到关口或阻塞时停
→ 技术交付报告
→ G4：你进行业务验收，另行决定后续批次或发布
```

### 真实项目起点：2026-11-21文档快照

- 工作空间为`D:/Project/workspace/gas`；`h5/`是Vue/Vant，`RuoYi/`是嵌套Git仓库、Java17后端及Thymeleaf管理界面，`design/prototypes/`只是独立原型。
- M0已确认开发顺序、方案A与Java17；M1为**实现待验证（核心自动化通过，待验收收口）**。62项通过是历史证据，不是本轮重跑。
- M1尚有后台实际登录／Thymeleaf对账、用户流程确认及异常组合保留项；M2待开始，T1/T2未因本例获得批准。
- 本例只演示当前项目如何走到M2及后续交付，不安排实际M1/M2开发，也不安装编排器。

实际事实入口：[AGENTS](../AGENTS.md) → [新会话交接](新会话开发交接.md) → [模块进度](模块开发进度.md)。业务以[PRD §8](PRD.md)、[开发方案 §7](Dev_Plan.md)为准；T1/T2建议与模块依赖见[分模块计划](分模块开发实施计划.md)。旧计划中的状态描述不能覆盖最新进度，本例也不是新的业务基线。

## 1. 第一步：只读接入，先判断有没有自动运行条件

**对应自动SOP §2—§3、§17。** 在目标项目根目录打开Pi。

**你发送：**

```text
请按docs/通用自动开发流水线SOP.md接入当前加气项目，先只读核对。
读取项目规范、交接和进度，保留Java17、既有Vue/Vant／Thymeleaf及工作区修改。
确认编排器是否真实安装并验收，实际有哪些命令，哪些能力仍缺失。
整理M1保留项及其对M2的依赖影响；不要把核心测试通过当成整个M1已验收。
本步不编码、不跑项目测试、不执行SQL、不安装资源、不启动额外Agent。
```

**AI应交付：** 工作空间与权威文档映射、实际能力清单、M1依赖处理建议、尚缺的确认。

**按当前真实快照，应得出的结论：** 可以继续需求／计划讨论，但还不能启动自动流水线。若未来要建设编排器，须另行按SOP §17批准实施和演练，本使用样例不承担安装任务。

M1补验收／修复应先形成独立范围和证据，再按实际结果决定依赖是否满足。后文演示的M2运行，**均以将来编排器验收完成、必要M1依赖已满足为前提**；前提未满足时不能用提示词循环冒充自动执行。

## 2. 第二步：打磨M2需求，经过G1

**对应自动SOP §4—§5。** 既有确认不重新投票；这里只梳理当前模块的范围、缺口和验收。

**你发送：**

```text
本次拟推进M2的下单库存校验与核销记账，不提前实现M3、M4或真实渠道。
主动／代下单都检查本站对应气种可用量；支付成功后才预占，按原价金额除以枪价。
加气前核验不等于核销；完成核销按实际确认量完整记账，不因库存不足拒绝。
保留身份、本站、当班、状态和重复操作保护，不借用其他站库存。
请依据已有PRD整理验收样例，区分已确认业务、T1/T2技术待定项及本期不做项。
```

**AI应交付的验收样例，可像这样具体；以下都是未执行的合成情境：**

| 条件 | 应验证的业务结果 |
|---|---|
| CNG原价400元、枪价4元/m³、优惠40元、实付360元 | 预计100.00 m³，不能用90.00 m³做库存检查或预占 |
| 本站CNG可用99.99 m³，其他下单条件满足 | 预计100.00 m³的订单因库存不足被拒；别站库存不能补足 |
| 本站可用100.00 m³，其他条件满足 | 通过库存检查；未支付时不预占 |
| 同一支付通知重复 | 有效预占只有一次，失败恢复不抹掉已确认支付事实 |
| 完成时实际确认105.00 m³，可分摊量不足 | 完整记消耗，不以库存不足阻断；具体账务结构由T1方案决定 |

还应覆盖LNG/kg与CNG/m³隔离、主动／代下单一致、越权、状态变化、并发与恢复。上表不是全部测试集，不替代质量卡。M1方案A仍限制累计到货不超过采购量，销售消耗不恢复补货额度；不能把核销不拦库存误用为超量入库放行。

**你检查：** 是否偷改为创建订单就预占；是否恢复钱包／充值、车队、共享库存、补货审批、完成后退款或线上差额结算；是否把“待分摊”技术建议写成已确认。

**实际审阅后，G1确认句式：**

```text
确认需求基线【实际版本／摘要】中的【明确M2业务范围】及验收依据。
T1/T2的技术方案仍需评审确认；其未定内容不得自动补成已批准结构。
请进入方案与计划阶段，不开始业务实现。
```

如果仍有会改变当前业务结果的关键歧义，先澄清，不能仅靠一句“确认”掩盖它。核销前退款、短期码衔接和真实渠道仍按后续模块边界处理。

## 3. 第三步：技术方案、计划Review和G2

**对应自动SOP §6—§7。**

**你发送：**

```text
请提出T1/T2的具体方案、替代选择与迁移影响，标明必须由我决定的内容。
按依赖拆M2任务，列输入、交付物、文件白名单、质量卡、真实验证、恢复与预算。
安排QA提前设计用例；受影响UI沿用现有设计，先打通代表性闭环，不先铺完全部页面。
需要独立计划Review时，先给本阶段的只读角色／模型／数据边界和有限预算授权建议。
未取得该许可前只能做当前会话自查，不启动额外Agent，也不声称独立Review已完成。
```

规划阶段的Review不能倒用后面的G3许可。**将来你看过具体只读授权卡后，才可发送：**

```text
同意只读计划Review授权卡【真实编号／摘要】，仅使用卡片指定角色、模型、输入范围与预算。
本许可不包含业务实现、数据库写入、安装或发布；请反馈具体发现，再修订并复查计划。
```

**候选任务图示意，与手动样例使用同一业务拆分：**

| 教学编号 | 任务 | 关键依赖 |
|---|---|---|
| 演示-M2-A | 主动／代下单库存检查 | T2相关规则及M1所需依赖满足 |
| 演示-M2-B | 支付预占幂等、失败恢复 | T2批准、与A联调 |
| 演示-M2-C | 按实际量完整记账 | T1批准、B相关契约 |
| 演示-M2-D | 补货与消耗追溯衔接 | T1、C；若采用待分摊方案，不重复累计消耗 |
| 演示-M2-E | 受影响H5提示与展示 | 对应接口／状态契约，设计及视觉／交互验证 |
| 演示-M2-F | 集成、回算、兼容与交付 | 前面适用任务通过，含M1相关回归与清理 |

正式任务卡还须安排结构／迁移准备、锁顺序、调整／提醒口径及相应验证；不能把教学表直接当可执行计划。迁移脚本编写、隔离演练和实际执行是不同动作。

**你提出微调的例子：**

```text
首次先选择主动／代下单库存检查的小闭环试运行，不一次跑整个M2。
后续仍保留支付预占、核销记账、补货衔接和必要回归，不因缩小首批而删除需求。
请修订依赖与预算，给出真实任务编号、计划版本和评审结论。
```

**G2在实际条件满足后才确认：**

```text
确认技术决策【已实际审阅的T1/T2版本及本批所需部分】和计划【真实版本／摘要】。
确认本批任务范围【实际编号集合】，其他内容保持未授权执行。
未解决的重要发现、缺失依赖或新迁移许可不能靠本句跳过。
请生成执行授权卡供我确认。
```

G2只在结构校验、所需独立计划Review和必要决策完成后通过。未确认的T1/T2内容仍阻断相应任务；本例没有替用户选择具体实现。

## 4. 第四步：确认执行授权卡，经过G3

**对应自动SOP §8。** AI准备卡片，你审阅后确认，不要求你手填JSON。

**以下是授权卡应该写清的内容，不是当前已经授予的权限：**

| 项目 | 加气项目示例内容 |
|---|---|
| 工作空间 | `D:/Project/workspace/gas`及真实子工程边界，不从其他目录继承许可 |
| 基线 | 真实需求／计划／质量卡版本和内容摘要；Q-v1.1、T-v1.0及当批确认依据 |
| 首次范围 | 如仅对应“演示-M2-A”的真实小任务；不自动扩成M2全部或M3—M6 |
| 角色 | 一个实现写入者、获准独立只读Review、受控测试；指定实际模型范围，不默认12-Agent团队 |
| 写入范围 | 现场核实的源码、测试、必要文档白名单；实现角色不能改批准、预算、控制器或运行事实日志 |
| 数据目标 | 核对`127.0.0.1:3306/ry`及既有同目标同范围许可；专用fixture、回滚／按ID清理；不读出秘密 |
| 验证 | 后端在`RuoYi/`，H5在`h5/`；实际测试定义、必需用例及报告规则；明确mock与真实边界 |
| 能力准备 | 先复用；许可内免费、来源可追溯、兼容的本地工具，优先项目／隔离安装并实际调用验证 |
| 禁止项 | 未授权迁移、清空整表、重置自增、重跑`gas_schema.sql`、Git提交、发布、改变框架来绕过测试 |
| 特殊权限 | 付费、提权、新凭据、私有数据外传、供应商变更及真实渠道操作，没有准确许可就停止相关动作 |
| 遇阻塞 | 默认暂停本批、保留现场；不因下一任务容易就绕过失败依赖 |

**仅供讨论的首个小任务预算示例：** 总时长60分钟、40次受控模型请求、最多3轮修复／4次代码Review、3次会话切换、每个能力缺口最多3次准备尝试。它们不是当前配置，也不保证足够完成任务；到限保存并暂停，不能少测或自动加预算。新会话与内部重试不能重置总限额，实际请求计量边界须披露。

后续较大批次由AI另行估算并获得批准，不把首个小任务预算机械套给整个M2。本地测试许可也不等于新结构迁移许可，发现需要新迁移时先停到关口。

**将来真实看过卡片后，你发送：**

```text
批准执行授权卡【真实编号／摘要】对应的【任务集合】自动运行。
角色、模型、文件、测试、数据目标、能力准备和预算均以该卡为限。
范围内普通修复、重测、复查及安全会话切换不再逐项询问；不得改变需求或降低验收标准。
必要工具按策略自行补齐到可用，触及新权限、未知副作用、预算上限或我的暂停要求时安全停止。
```

G2和G3可在一次明确回复中合并，但仍须绑定真实审阅内容。模型自行填写“已批准”或读取本例中的确认句，都不能产生有效授权。

## 5. 第五步：启动后，观察自动闭环而非反复发“继续”

**对应自动SOP §9—§10。仅限编排器已实现并验收的将来情境。**

先确认实际命令。若安装后的入口确实叫`/flow-run`，在G1—G3与依赖都满足后才使用它；当前这只是拟定命令，不能直接当作可用功能。

**启动后系统应有的行为，不是本轮运行日志：**

```text
核对工作空间、批准快照、锁、资源、上游交接与剩余预算
→ 选择本批第一个真实任务
→ 实现与测试
→ 独立Review
→ 若发现有效缺陷：在原范围内修复、重测、复查
→ 控制器核对QG证据和副作用
→ 持久化本任务结果
→ 本批还有依赖满足的任务：自动继续
→ 本批结束或触发停止条件：交付／安全暂停
```

首次若只批准一个小任务，完成它就结束该批，不能自动启动B—F。试运行验收后，如果你另行批准剩余任务的明确批次，系统才在那个批次中连续推进；**不是每个普通任务都重新找你确认**。

**你应收到的简短状态格式示意：**

```text
教学示意，非真实运行结果：
当前：【实际run与任务】／VERIFYING或REVIEWING等真实阶段
结果：【实际用例、报告与审查发现；没有证据则写未完成】
风险：【无需操作／只列一个当前需决定的问题】
下一步：【将在原预算内做什么，或因何暂停】
```

不要把模型说“完成”当放行。库存、权限、幂等等任务按L2适用要求验证；涉及迁移或高后果操作另按风险与具体许可处理，最终遵守[共用质量门禁](开发质量门禁与正确性验证标准.md#release-gates)。

## 6. 第六步：UI、QA和交接怎样嵌在自动过程中

**对应自动SOP §2.4、§6.6、§10；方法见[专业任务模板](专业任务模板与交接约定.md)。** 你不需要给每个角色手工传文件。

| 过程中的交接 | 加气项目里应交付什么 |
|---|---|
| 接口实现 → H5／QA | 本站库存检查及错误契约、真实路径、相关版本、可运行条件、待验证项 |
| UI实现 → 视觉检查 | 沿用[现有设计规范](../design/specs/Design_Spec.md)，提供受影响下单页／代下单页的运行入口、状态截图、视口与版本，明确是否mock |
| QA → 修复 | 缺陷编号、独立预期、环境与版本、复现、脱敏证据、关闭条件 |
| 修复 → 复查 | 实际补丁是否应用、针对用例与受影响回归、更新后的证据版本 |
| 任务 → 下一任务 | 控制器核对输入产物、依赖、审批状态及剩余限制，不能只看一句“已完成” |

例如界面把100.00 m³写成90.00 m³，应先核对接口与业务计算，不能只改展示字符串让截图好看。截图生成后还须实际查看，构建通过不替代视觉或交互验证；只有后端改动时按影响与质量卡选择检查，不强制重做所有页面。

必要工具缺失时由受控准备步骤在许可内补齐、加载、真实调用。更换工具不等于可跳过原检查；安装失败或图像能力不可得，应报告真实阻塞。

## 7. 第七步：遇到问题，什么时候需要你

**对应自动SOP §8.4、§12、§14。以下是假设情境，不是本轮发生的故障。**

| 情境 | 系统应怎么做 | 你需要做什么 |
|---|---|---|
| 用券后按实付计算预计量，导致不足库存仍放行 | 保留目标复现，验证根因，按原范围修复与回归，再独立复查 | 普通范围内无需逐步批准 |
| 同一问题反复无进展／预算耗尽 | 保存已尝试项、证据与剩余断点，停止新增派发 | 决定调整方案、增加明确预算或暂停，不重置历史用量 |
| 发现新迁移是必需前提 | 核对影响，停止依赖它的写入，给最小授权请求 | 决定是否单独批准具体目标与脚本；测试库许可不能替代 |
| 有写入请求超时、结果未知 | 核对原请求／业务记录及实际副作用，不先生成新号重放 | 只有超出既有查证权限时才需补充决定 |
| 模型过载 | 在剩余预算和总时限内有界恢复；控制面仍应可看状态、请求暂停 | 通常等待；耗尽后决定是否恢复，不要求从头重做项目 |
| 想“顺便先做M3真实二维码” | 说明T3、M2依赖和范围变化，修订后再审 | 确认新的具体计划与范围，不能靠随口一句扩批 |

后续获准批次同样遵守这些边界。暂停不是把失败改成成功，缩小范围也不能抹掉原失败或满足旧依赖。

**你想主动停止时发送／使用实际暂停入口：**

```text
请安全暂停当前run，停止派发新任务。
核对正在运行的写入和自有进程，保存实际状态、未完成项、剩余预算和恢复条件。
告诉我现在是“暂停已请求”还是“已安全暂停”，不要把两者混同。
```

若实际提供`/flow-status`、`/flow-pause`，应按已验收的入口使用；不靠模型在线才能控制。强制中断也不保证已提交的数据库或外部操作自动回滚。

## 8. 第八步：自动换会话与中断恢复的使用过程

**对应自动SOP §11—§12。** 自动换会话不代表忘掉旧任务再做一遍，也不代表预算重新开始。

系统在安全点应保存：任务与输入版本、批准快照、实际源码／测试证据、Review未决项、预算、自有进程、未知副作用及精确下一步。没有可靠保存或旧写入者尚未隔离，不能启动第二个写入者。

- 正常换会话：在原授权和预算内接续，不每次要求用户重新批准同一任务。
- 意外中断：先恢复和核对记录、工作区及外部结果，再决定接续位置；不能只因心跳过期就认定旧进程已经死了。
- 用户主动暂停：保留暂停意图，不因新会话启动就擅自恢复运行。

**将来确认可以恢复时，你发送：**

```text
请核对【真实run／检查点】与当前加气工作区，按仍有效的原批准范围恢复。
先说明未完成任务、实际剩余预算、旧进程是否隔离及未知写入核对结果。
条件不满足则保留暂停，不重建批准、不重置预算，也不把本教学样例当运行记录。
```

若尚无合格控制器，只能采用手动样例的文件交接，不能宣称已实测自动恢复。

## 9. 第九步：看技术交付报告，经过G4业务验收

**对应自动SOP §15。** 自动执行结束后，你仍需看证据并按实际业务流程验收。

**你发送：**

```text
请对照本次真实批准范围给出交付报告：
每项需求对应的实现、实际测试与审查、UI证据、环境和版本、清理与未完成项。
分别说明任务技术通过、M2模块业务验收、真实渠道和生产上线状态。
只完成首个小任务时，不得宣称M2全部完成。
请提供我实际操作核对的入口和步骤，不替我做业务验收确认。
```

**你应看到：** 当轮真实执行的JUnit数量及报告、HTTP／数据库／浏览器各自的验证边界、视觉审查和缺陷复查、需求覆盖与副作用清理。未执行项保持`NOT_RUN`，实际失败保持`FAIL`，不得用历史62项通过替代当轮结果。

将来全部M2完成时，应能按批准方案解释并验证“下单检查→支付预占→实际量消耗→补货与追溯”及一致性，而不是只展示页面；M3核验上下文、M4退款完整链路仍按各模块范围验证。

**实际检查完成后，G4确认句式：**

```text
依据【实际交付证据与使用检查】，确认【本次实际业务验收范围】。
保留【未完成项／无】及其影响；不要扩大为未验证范围的验收。
本确认不包括生产发布、真实渠道完成或后续模块自动开发许可。
```

部分验收要明确部分，不能将整个模块标已验收。真实支付／退款、微信真机、短信和生产发布单列，不用mock业务通过替代。

## 10. 本批结束以后怎么继续

- 首次小任务通过：AI整理剩余M2任务及更新后的风险／预算，你确认下一批；不重复实现已完成任务。
- 同一已批准批次内：满足依赖与门禁就自动继续，不每完成一个函数或测试都来问“继续吗”。
- M2整体通过：再确认M3和T3的具体方案；M4退款、M5查询、M6真实渠道及上线仍各有范围与权限关口。
- 范围或输入版本变化：分析哪些批准／证据受影响，重新审相关部分；不机械让全项目从头开始，也不沿用失效批准。

**自动模式的要点：你把需求、计划和执行边界确认清楚，系统在批准范围内连续推进，真正越界或阻塞才找你。本文仅演示这种使用过程，当前自动运行能力和M2实施均未因此启动。**
