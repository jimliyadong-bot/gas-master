# 开发质量门禁与正确性验证标准

> 版本：Q-v1.1｜修订日期：2026-11-21｜适用：手动步进与自动流水线，所有已接入工作空间。
>
> 本文件是 [手动版SOP](通用项目流水线开发SOP.md) 和 [自动版SOP](通用自动开发流水线SOP.md) 共用的质量规则。两种模式可以采用不同调度方式，**不能采用不同的正确性标准**。
>
> **不保证代码100%正确，也不把测试通过或独立Review视为无缺陷证明。** 本轮建立的是规范，尚未实现机器门禁或执行本文试点；文档静态检查不等于业务验证。

**使用顺序：** [判风险](#risk-levels) → [生成质量卡](#quality-card) → [固定独立预期](#independent-oracles) → 实现／修复 → [核对放行条件](#release-gates)。专项入口：[红→绿证据](#red-green) · [不变量](#invariants) · [UI审美与专业度](#ui-quality) · [能力自动补齐](#capability-bootstrap) · [不偏离、不丢尾](#delivery-convergence)。

---

## 0. 怎么用，怎样避免增加负担

1. AI在拆任务时判断风险与影响边界，生成一张简短质量卡，和计划一起审核；不要让用户手填配置。
2. 需求、测试预期和必需检查先确定，再开始实现；既有系统按实际资料接入，不重做无关验收。
3. 普通任务采用适用的最小检查；关键逻辑增加对应真实验证与独立证据，不要求全项目统一跑重型测试。
4. 手动模式由操作者核对证据后决定推进；自动模式须由实际实现的控制器核验条件，不能靠模型自报成功。
5. 同一已批准质量卡在范围不变时持续有效，不逐次重复确认；业务行为、风险、必需场景或通过条件变化时重新审核。

项目规范和明确确认的业务规则仍有效。本文件不替用户解决待定需求，不授予数据库／发布／额外Agent权限，也不追溯宣称旧测试已经满足新门禁。

本文件统一维护风险与质量判据；两份SOP只引用其版本和任务质量卡。不要分别复制两套风险矩阵或通过阈值。工作空间可以增加更严格约束；无法满足本标准时报告差距，不能静默降低等级或标准。

<a id="risk-levels"></a>

## 1. 按影响分级，不按代码行数分级

### 1.1 四级风险与最低检查

| 等级 | 典型影响 | 最低检查要求 |
|---|---|---|
| L0 展示／说明 | 不改变运行行为的普通文案、格式、链接 | 范围核对、文档／格式检查、人工或当前会话复核；界面变更需相应展示检查 |
| L1 普通行为 | 局部功能、交互、一般查询或非关键计算 | 适用的静态／构建检查；正常、失败和边界行为测试；受影响回归与代码Review |
| L2 关键正确性 | 身份权限、敏感数据、主体隔离、金额／库存／账本、事务、并发、幂等、重要数据一致性 | L1＋独立预期；适用的不变量断言；触及边界的真实集成验证；实现上下文之外的独立Review或人工审查 |
| L3 高后果操作 | 正式或共享有价值数据的迁移／批量修改、不可逆外部操作、生产发布等 | L2的适用检查＋隔离演练、操作前后核对、可行的恢复／补偿方案、具体操作授权；默认不跨人工操作关口自动执行 |

**风险是质量要求，不是操作许可。** 标成L1也不代表可以未经允许联网安装依赖；获得测试库写入许可也不代表相关业务逻辑可以从L2降到L1。

### 1.2 分类规则

- 取受影响行为的最高适用等级，记录理由和标签，例如`AUTH`、`PRIVACY`、`ISOLATION`、`ACCOUNTING`、`CONCURRENCY`、`MIGRATION`、`EXTERNAL`、`UI`。
- 公共组件、依赖、工具链或配置的变更按实际影响范围分析；不能只验证眼前一个调用方就忽略其他受影响模块。
- 一行权限修改可能是L2；文档如果改变业务规则、发布指令或安全策略，不能因为扩展名是`.md`就归L0。
- 只修改规范文档时验证其定义、引用与一致性，不为此运行无关数据库测试；未来按规范实现的运行行为仍需另行验证。
- 真正没有影响的边界可以记录不适用，但“难测”“没有环境”“预算不够”不是不适用理由。
- 子任务可以细分验证范围，但不能通过拆小任务绕过整体一致性与集成检查。批次需按组合后的影响安排回归。
- 风险不明时先澄清；降低风险等级必须给出影响分析并重新审核，不能由实现者单方面降级。

### 1.3 “真实验证”必须对应实际边界

权限变化验证真实鉴权／服务端校验路径；事务与锁变化使用对应数据库和事务行为；UI交互变化验证实际组件／浏览器路径。不能一律要求所有L2任务都运行全部外部渠道测试，也不能用mock替代已经选定的真实验证。

迁移在隔离空库里演练不等于允许迁移正式数据。L3执行许可与其技术演练结果分开记录；所谓“回退”必须实际可行，不可逆动作不能伪装成随时可撤销。

<a id="quality-card"></a>

## 2. 一张任务质量卡，贯穿计划、实现和验收

可作为现有任务卡的一部分，不必再新建文件：

```markdown
### 任务质量卡
- 任务／需求／验收项：
- 质量标准：Q-v1.1；本卡版本／确认依据：
- 风险等级、标签及理由：
- 影响边界、明确不适用项及理由：
- 独立预期：来源、样例、计算／判断方法及批准版本：
- 必需检查：检查ID、命令／人工步骤、目录、环境、通过条件：
- 可执行不变量：规则ID、断言位置或不适用理由：
- 缺陷修复：复现编号；红→绿方法，或待审核的替代证据方案：
- Review方式：自查／独立上下文／人工，及重点：
- 前端适用项：设计基线、代表页面、终端／状态矩阵、UQ检查与视觉审查方式：
- 能力准备：已有／缺失技能、扩展或工具；安装授权、版本与真实调用证据：
- 需求闭环：正向覆盖与改动反向归属；当前未完成项及接续动作：
- 加强测试：是否需要性质／差分／变异测试，理由与预算：
- 证据绑定：源码、测试定义、关键依赖／非敏感配置、环境与报告引用：
- 未满足项、停止条件和后续处理：
```

必需检查集合与适用性在执行前审核。工具缺失时按 [能力自动补齐](#capability-bootstrap) 自行识别、安装／启用、调用并验证；已有明确安装许可时不重复询问，也不把本可自动处理的安装任务交回用户。没有许可或超出边界时先取得必要决定；不编造`npm test`等脚本、不以缺工具为由少测。

允许在既定需求内新增补充用例，经过Review并更新版本证据，不要求每条新断言都重新请用户批准。删减必需场景、放宽断言、调整验收语义或用更弱验证替换原要求，则必须进入变更审核。

**依赖质量卡的预算不足时，暂停、申请调整预算或修改批次范围；不能自动少测几项再放行。**

## 3. 独立预期：测试不能只证明“代码和自己一致”

### 3.1 什么可以作为预期来源

- 用户确认的业务规则与验收样例。
- 经核对的公开协议／接口契约与批准的兼容行为。
- 对小规模样例的人工推导、独立公式或简单参考模型。
- 由上述来源形成、经过审查的标准数据与结果集。

记录来源、版本、输入、预期结果及推导依据。对于已有系统，当前输出可以是现状证据，但只有经过确认的兼容行为才能作为正确性标准。

### 3.2 必须避免的同源错误

- 调用被测业务函数计算测试的预期结果。
- 把生产实现公式原样复制进断言，却没有独立核对业务含义。
- 直接录制当前错误输出，再把它当“标准快照”。
- 只让Review阅读实现者总结，或把换模型当成预期一定正确的证明。

相同AI分别写代码和测试，仍可能重复同一种误解。L2以上关键规则应至少有可核对的独立来源及代表样例；独立审查要检查预期来源，不只检查测试是否运行。

复用夹具构造、序列化等非被测业务辅助工具可以接受，但不能因此让预期值依赖同一条被测逻辑。

### 3.3 预期如何确定和变更

新行为尽量在实现前确定样例与验收预期；旧代码先从确认规则提取预期，不用现状反推全部规则。

需求改了可以改预期，但要关联新需求版本、影响分析和审核记录。更新快照不是普通“修复测试”捷径；只因为实现输出变了，不能自动刷新预期使测试变绿。

复杂或含糊规则先停下来确认，不能用更多测试掩盖没有正确答案的问题。

<a id="red-green"></a>

## 4. 缺陷修复：保留真实红→绿证据

### 4.1 可自动化缺陷的标准闭环

1. 冻结复现条件与预期，关联缺陷编号。
2. 在安全的缺陷版本上执行回归用例，确认它因目标缺陷失败，保存RED证据。
3. 修复实现；保持同一业务预期和可比输入。
4. 执行该用例得到GREEN证据，再跑受影响回归。
5. Review核对修复、断言与结果，确认不是通过删除或弱化测试解决。

RED必须是目标缺陷造成的失败。与目标缺陷无关的缺依赖、编译报错、连接错误或不相关超时，不能冒充RED。若目标本身就是构建／连接失败，须确认失败原因与该缺陷一致，并排除无关环境问题。

### 4.2 不破坏用户现场来制造RED

可以在本轮修改前测试，或在获准的隔离副本／工作区验证旧版本；不能reset用户工作区、回退未知修改、写正式数据或恢复秘密配置来复现。

修复已完成但缺少原版本时，不能临时制造另一个错误冒充原缺陷。应记录缺失情况并提出替代验证方案。

### 4.3 难复现与替代证据

生产偶发、设备限制、时序竞争或历史现场缺失时，可提出脱敏现场证据、受控时序复现、契约推导、性质／不变量检查等组合。明确哪些是已证实、哪些只是推断。

替代方案须按风险审核后进入质量卡；L2/L3不得由实现会话自行宣布“无需复现”。没有获准的充分替代证据时标`BLOCKED`，不能把RED写成已执行。替代证据获准也不意味着可以省略最终针对性回归。

测试内容因新的认识需要修订时，记录变更，重新检查其能否在相应缺陷版本上识别问题，不拿两套不相干的测试结果拼成红→绿。

<a id="invariants"></a>

## 5. 把关键规则写成可执行不变量

不变量是跨多组输入仍应成立的业务关系，应来自已确认规则；**不是通用模板可以替用户决定的业务规则**。

| 规则类型 | 可验证关系示例 | 注意 |
|---|---|---|
| 幂等 | 同一业务标识重复处理，事实只生效一次 | 同标识不同输入怎么处理须先确认 |
| 隔离 | 操作主体A，不改变或泄露主体B的记录 | 不能只验证页面没有显示B |
| 事务 | 失败后，批准的原子性边界内保持一致 | 外部已收款等事实不一定随本地事务回滚 |
| 账本 | 按确认口径，事实、汇总与明细可重算核对 | 不擅自假设所有库存／余额永不为负 |
| 状态机 | 非法转换不成功，合法转换留下正确事实 | 并发操作也需符合确认的最终结果 |
| 数值 | 精度、单位、边界与舍入符合确定规则 | 测试预期不要复用被测计算函数 |
| 恢复 | 结果未知时查询／原号恢复不重复生效 | 无法查证的不可幂等操作必须暂停 |

质量卡记录规则ID、断言位置、输入范围及对应检查。只有文字描述而没有检查，不算“已验证不变量”。

L2及以上对其适用的关键不变量建立可重复检查；可以先用确定样例与状态快照，再根据风险选择生成数据、参考模型或真实并发验证。

并发测试应设计受控交错、同步点与最终状态核对。跑几次没有报错不能证明所有竞态已消除；发现失败时保留调度条件和最小复现资料。

## 6. 共用放行门禁：有证据才算通过

### 6.1 八项门禁

| 编号 | 判断什么 | 阻止技术放行的情况 |
|---|---|---|
| QG-01 | 需求、范围、风险与必要批准明确 | 关键规则待定、未授权操作、实际风险超过批准范围 |
| QG-02 | 预期来源独立且可追溯，前端有设计依据 | 只与实现自身比较，关键样例／契约／必要设计方向未确认 |
| QG-03 | 改动范围、能力准备、静态／构建与基线检查合格 | 越界改动、必需能力未实际可用、适用必需检查缺失或失败、重要基线差异未解释 |
| QG-04 | 必需行为测试及缺陷证据满足质量卡 | 零用例、必需项跳过、目标缺陷未被识别、缺获准替代证据 |
| QG-05 | 适用不变量与真实边界已验证 | 只写规则未检查、用mock冒充原定真实集成验证 |
| QG-06 | 所需代码及视觉Review完成且发现已处理 | 必需审查缺失、前端UQ适用项未通过、无有效结论、本次范围及必要依赖内仍有未解决阻断／重要缺陷 |
| QG-07 | 证据属于当前最终版本 | 证据与当前任务相关版本不符，或变更后未核对影响直接沿用旧报告／Review |
| QG-08 | 副作用可确定，需求与交付双向对齐 | 未知写入、自有fixture未核对、本批必需项遗漏、无依据新增／替换功能、把技术通过写成人工验收／上线 |

L0可以用文案依据／预期展示作为QG-02证据，用文件或页面检查作为QG-04证据；不因表格中有“测试”二字就要求无关数据库测试。QG-05无业务状态时可以不适用，但要有理由。

### 6.2 检查状态与严格判定

检查项状态统一区分：`PASS`、`FAIL`、`NOT_RUN`、`BLOCKED`、`NOT_APPLICABLE`。

- `PASS`：已有当前版本有效证据，满足事先确定的通过条件。
- `FAIL`：检查实际执行且不满足条件，不能用一句“可接受”改写历史。
- `NOT_RUN`：尚未执行，不是通过。
- `BLOCKED`：前提、权限、证据或能力缺失；写明恢复条件。
- `NOT_APPLICABLE`：已批准质量卡或已批准的适用性变更确认与当前范围无关，有理由；不能由实现者自行把缺环境或测试失败转换而来。

技术放行必须同时满足：

```text
质量卡与批准版本匹配
且每个适用的必需门禁都有有效PASS证据
且不适用项有经审核的理由
且本次放行范围及必要依赖内不存在未解决的阻断／重要缺陷或未知副作用
且最终源码、测试定义与报告／Review对应
```

必需用例skip不等于`NOT_APPLICABLE`。非必需测试的跳过也必须记录理由；不能利用过滤器把必需场景排除后声称通过。

### 6.3 例外、基线失败与范围变更

既有失败要精确关联用例／问题与版本，分析是否影响当前改动。必要时分离不受影响的验证、明确批准本批范围；不能笼统忽略全部旧失败或改退出码期望来制造成功。

用户可以决定延期、缩小交付范围或接受残余风险，但这些决定不是失败测试变成成功的证据。需重新审核计划、依赖和批准快照；受影响任务仍不满足原退出条件，交付报告保留限制。

必需安全约束、真实批准、证据真实性和未知副作用核对不能由模型豁免。对于重新批准的更小范围，只能宣称该范围通过，不能替整个原模块签字。

### 6.4 证据绑定与过期

记录需求／计划／质量卡版本、测试时间、相关源码与测试定义摘要、工具及关键依赖版本、必要非敏感环境信息、命令、报告和Review引用。

HEAD相同不证明未提交文件没变。只对明确范围内的非敏感文件保存内容指纹；不要记录或哈希密码、令牌等秘密。报告必须来自对应执行，不能只按文件名找到一个旧成功报告。

修改后先做影响分析：受影响证据必须重做；确实不受影响的历史证据可有理由地沿用，不能把“版本绑定”变成任何文档改动都全量重跑，也不能用“无影响”逃避实际代码变化。

## 7. 加强测试按风险选，不一刀切

| 方法 | 适用价值 | 限制与控制 |
|---|---|---|
| 性质／属性测试 | 多组输入验证不变量、状态与边界 | 固定或记录随机种子、范围及最小反例；仍依赖性质本身正确 |
| 差分／参考模型 | 将结果与简单独立算法或批准参考结果比较 | 不共享被测缺陷路径；参考模型也须审查 |
| 变异测试 | 在隔离副本故意改变比较符／分支等，观察测试能否发现 | 选关键逻辑和有限预算；存活变异分析等价性，不追逐统一100%指标 |
| 受控并发／故障注入 | 复现竞争、部分失败、未知结果和恢复 | 仅在获准隔离环境，记录调度与副作用，不破坏用户服务 |
| 实际界面／人工探索 | 检查交互、视觉、设备与可访问性问题 | 明确步骤、环境和结果；不能用截图替代后端事务检查 |

L0/L1不默认要求性质、差分或变异测试；L2/L3在计划审核时判断关键规则是否值得采用，并记录理由。已确定为必需的加强检查不得因执行困难自动取消。

覆盖率、用例数量、Review次数都是辅助信息，不单独证明正确性。先确保测试能识别关键错误，再讨论扩大覆盖。

## 8. 小任务试点：验证规则确实能拦错

建议先选一个低风险、可隔离的小任务演练，再扩大自动运行范围。以下为**待执行的验收场景，本次文档优化未执行它们**：

| 编号 | 场景 | 应有结果 |
|---|---|---|
| QV-01 | 普通文档／文案小改动 | 按适用L0检查，不强迫运行无关数据库测试 |
| QV-02 | 只有一行代码的权限／金额逻辑变化 | 不按行数判低风险，生成相应关键检查 |
| QV-03 | 测试预期直接调用被测业务函数 | 审查指出预期不独立，不能仅凭测试绿放行 |
| QV-04 | 可复现缺陷，旧版本失败、修复后通过 | 保存可比红→绿和回归证据；环境错误不冒充RED |
| QV-05 | 必需测试零用例／skip／报告缺失 | 阻止技术放行，不转成不适用 |
| QV-06 | 改源码／测试定义后复用旧报告或Review | 识别证据过期，重验证受影响范围 |
| QV-07 | 缺真实数据库环境，却给出mock成功结果 | 标阻塞或申请变更，不声称原要求通过 |
| QV-08 | 独立Review失败或仍有重要发现 | 不因缺结论或模型自我销项而放行 |
| QV-09 | 在隔离副本注入一个应被覆盖的关键逻辑错误 | 对应检查确实失败；若未发现则补强测试而非忽略 |
| QV-10 | 预算耗尽后要求跳过失败检查继续 | 停止并给出选项，不自动降低门槛或换会话重置预算 |
| QV-11 | 前端构建成功，但页面错位、图标缺失或仍是未批准的样式 | 真实渲染／视觉审查发现问题，修复复查前不放行 |
| QV-12 | 页面变好看，但少了权限提示、确认或错误恢复入口 | 行为及需求核对阻止以美化替代业务要求 |
| QV-13 | 必需能力缺失，已获安装许可 | 自行审查来源、安装启用、真实最小调用成功后接续；不要求用户手动安装 |
| QV-14 | 安装失败、资源同名冲突或宿主跳过加载 | 识别不可用，有限修复／等价替代；不把安装退出成功或宿主启动当能力可用 |
| QV-15 | 新资源要求付费、提权、上传源码或改变模型供应商 | 只请求相应缺少的决定，不利用安装许可扩大权限 |
| QV-16 | 中断恢复后少了一个验收项，或私自加入无关功能 | 双向追踪发现偏离；保留原范围与未完成项，不假报交付 |

先检查文档与模拟判定，再做获准的小任务真实演练。自动编排器未实现时可人工执行相同质量标准，但必须如实标注“人工核对”，不能宣称机器门禁已生效。

变异／故障只能注入专用副本或fixture，不修改用户有价值数据。角色会话、工具安装、外部调用和数据写入仍需对应许可，本清单本身不是执行授权。

## 9. 两种SOP如何接入本标准

| 阶段 | 同一质量要求 | 手动／自动的区别 |
|---|---|---|
| 需求确认 | 固定规则、预期来源和验收样例 | 都需要真实确认，不由模型代签 |
| 计划审核 | 风险分级、质量卡、必需检查与审查方式 | 手动由人逐步推进；自动绑定可执行计划与批准快照 |
| 实现／修复 | 同一红→绿、不变量、Review与回归要求 | 调度者不同，不降低验证强度 |
| 放行 | 按QG-01—QG-08判断，保留未满足项 | 手动核对记录；自动由控制器据证据执行，不能只读模型PASS |
| 交接／恢复 | 保存质量卡版本、缺陷与过期证据状态 | 都不能在新会话中丢失未通过项 |

L2/L3要求的独立审查可以由获准的独立会话或合适的人工审查完成；未获准启动额外Agent时先提出需要，不能默默委派，也不能用同一实现上下文自查冒充独立审查。

全局工作流打包时携带本标准或版本一致的规则资源，不运行时依赖某个业务目录。标准版本升级应明确影响：已运行批次不静默切换判据，按影响审核并记录适用版本。

**使用时只记一句：先确定什么算对，再根据风险验证；证据不够就补齐，确有阻塞则保全现场，不能用“流程走完了”代替正确性判断。**

<a id="ui-quality"></a>

## 10. 前端交付必须兼顾审美、专业度与行为正确

### 10.1 先定设计方向，再批量实现

“能显示、能点击、构建成功”不是UI交付标准。涉及界面时，AI负责设计、实现、真实预览、审查和迭代；不等用户发现明显粗糙后才补美化。

- 复用项目现有品牌、设计规范、组件库和已确认页面；不能为展示能力擅自换框架或整站风格。
- 新产品、主要页面或风格重构先形成简短设计基线：使用者、核心任务、终端、信息密度、风格关键词、参考依据、字体／字号层级、色彩、间距、圆角及组件规则。优先给一个推荐方向，确有分歧才给少量备选。
- 先做代表页面／关键状态的样稿或可运行预览，结合需求／计划一并确认方向，再推广到其他页面。既有方向明确时直接沿用；获准方向内的小布局、排版和间距优化自动完成，不逐个颜色请示。
- 风格要服务产品：后台强调可扫读与效率，移动业务页强调清晰和操作，品牌展示页可更有表达。不把大渐变、满屏卡片、过多阴影／动画当作通用“高级感”。
- 没有参考图时AI应主动提出方案，不无限等待用户当设计师；但不能替用户确认尚有分歧的关键设计方向。

### 10.2 八个专业度检查维度

| 编号 | 维度 | 可观察的通过条件 |
|---|---|---|
| UQ-01 | 任务与视觉层级 | 关键信息和主操作突出，分组／阅读顺序符合任务；不是所有区块同等抢眼 |
| UQ-02 | 排版与构图 | 字体层级、对齐、间距与留白有规则；数字／单位可扫读，无文字挤压或随意断行 |
| UQ-03 | 色彩与品牌 | 主色、语义色和背景一致，强调克制；成功／警告／危险不只靠颜色辨识 |
| UQ-04 | 组件与资产 | 按钮、表单、卡片、表格、弹窗和图标风格一致；无缺字、破图、未解析图标或未经确认的开发占位资产 |
| UQ-05 | 内容与状态完整 | 使用真实业务语义；适用的加载、空、错误、禁用、成功、长文本及大数状态均有明确呈现 |
| UQ-06 | 响应式与适配 | 目标尺寸／缩放下无非预期横向溢出、遮挡、截断；底部安全区、弹层与键盘影响按终端检查 |
| UQ-07 | 交互与反馈 | 导航、提交、取消、校验、焦点和反馈明确；主流程可操作，美化不破坏确认、权限、幂等或恢复 |
| UQ-08 | 可访问性与性能底线 | 对比、可访问名称、键盘／焦点及触控区域适用检查通过；动效可克制／降级，不以美化引入不可接受的加载负担 |

每个适用维度记录PASS／FAIL／NOT_RUN等状态、依据与缺陷，不用平均分掩盖单项失败，不把AI自评“90分”“高级”当验收证据。前端技术放行要求适用UQ项及原有功能检查均满足；设计偏好仍可在用户验收时提出并按变更影响处理。

网页默认检查普通文字对比至少4.5:1、大字至少3:1，定义与例外参考[WCAG文字对比说明](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)。移动主要操作以44×44 CSS px触控区域为设计目标；不要误写成所有控件的AA最低要求，[WCAG 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)的最低要求是24×24 CSS px并有间距等例外。适用例外须有依据；不能仅据这些检查宣称完整WCAG符合性。

### 10.3 必须查看真实渲染，而非只读CSS

1. 计划列出受影响页面、复用组件、关键状态和目标终端矩阵。按产品选最小目标宽度、常用宽度及适用宽屏；不把某个项目的390px写死给所有项目。
2. 在实际运行页面中操作主流程，核对控制台／资源加载、组件渲染、布局与反馈。mock数据须标注，不能冒充真实接口或真实设备结果。
3. 保存最终相关版本的关键截图，改造任务保留可比前后图；大范围改造先验证代表页，再检查全部受影响页面，不用一张首页截图代替全站检查。截图采用合成或脱敏数据；发送外部视觉服务须满足数据及模型调用许可。
4. 由具备图像能力的获准审查上下文或合适人工**实际查看截图／页面**，对照设计基线逐项检查。代码Review和“截图已生成”都不能替代视觉审查；小范围调整可按质量卡复核，不强制新增Agent。
5. 修复视觉／交互发现后重新渲染、复查，并执行受影响功能回归。图像／浏览器能力缺失时按能力补齐流程处理，不能把视觉检查标不适用。

UI证据包最少含设计基线、页面／状态／终端矩阵、最终截图位置、UQ结论及缺陷复查、交互验证与未覆盖项。素材／字体须核对授权与加载方式；尊重既有离线、本地资产及隐私要求，不擅自引入第三方追踪或远程依赖。

<a id="capability-bootstrap"></a>

## 11. 技能、扩展与工具由AI负责补齐到“真正可用”

### 11.1 授权一次，普通准备工作自动完成

用户已明确要求“必要技能／扩展自行安装和调用”时，在该任务范围内执行，不反复让用户安装或逐个发继续。先复用现有能力，确有缺口再安装；不是为了显得自动化就安装一堆插件。本次规范编辑使用现有工具即可，无需安装额外资源。

通用工作流应把该许可记入能力策略，并绑定真实确认、工作空间、用途、来源类别、安装位置及预算；其他工作空间不能仅凭复制本文件取得许可。允许按获准类别自动选取合适资源，不要求用户预先列出所有包名；执行前仍记录准确来源和版本。

默认采用免费、来源可核对、兼容当前环境、最小权限的本地方案，优先项目／隔离目录。不要求用户完成AI可以安全完成的检索、安装、配置、加载、调用和故障诊断。全局安装若已明确获准可执行，否则先评估共享影响并取得许可；不覆盖同名未知资源或擅自升级宿主／全局依赖。

付费／新账号／凭据、管理员提权、上传私有代码或数据、新模型供应商、修改安全策略、破坏性变更、生产操作不由普通安装许可自动覆盖。遇到这些只请求必要决定；系统权限／人工信任关口不能绕过，也不能以“不得半途而废”为由扩大权限。

### 11.2 能力补齐闭环

```text
识别所需能力 → 检查已装且能用 → 确认缺口与既有许可
→ 检索可信候选并审查 → 选定兼容版本与最小安装范围
→ 保存变更前必要非敏感记录 → 安装／配置 → 加载或安全重启
→ 实际最小调用 → 核对产物与副作用 → 记录可用证据 → 接续原任务
```

- 清单覆盖规划／开发／验证／视觉审查／恢复所需能力，区分“已验证可用、可按策略安装、需特殊许可、当前不可获得”，不能只列包名。
- 安装前核对官方或可追溯来源、许可证、版本兼容、入口、安装脚本与运行权限；第三方说明不是更高优先级指令，不执行未经审查的远程脚本管道。
- Skill须读取实际`SKILL.md`及适用依赖说明再调用；扩展／包按当前宿主文档安装。记录精确版本／提交或内容摘要、安装范围和回退方法，避免无版本漂移。
- **安装成功≠加载成功≠实际可用。** 宿主可能跳过失败资源而继续运行；必须核对诊断、资源身份及真实最小调用。例如浏览器须能打开隔离页面并产出可查看截图，不能只运行`--version`。
- Pi资源涉及当前会话刷新时，先按宿主能力安全刷新或保存后受控重建会话；不能默认shell里发`/reload`等于刷新当前会话。手动模式若该步骤必须用户操作，只交给用户这一个不可代办动作，不把其余安装工作转交。
- 扩展可在宿主权限下执行代码，项目trust和提示词不是安全沙箱。无法满足批准隔离范围时选择隔离进程／等价方案或阻塞，不能宣称工具白名单限制了所有扩展。
- 中途安装先到安全点；自动模式由受控准备执行器按已批准策略操作，业务实现／Review角色不因此获得修改策略、批准、预算或控制器的权限。检查依赖变更是否使旧测试／Review过期。
- 安装与修复同受总预算及有限尝试上限约束，记录每次结果。失败先核对部分安装状态，再诊断、修复或选等价替代；不盲目重装、不清理用户文件。替代不能降低验证能力、改变业务需求或越过网络／数据许可。

没有可信可用方案时给出已尝试项、具体原因、可选方案和最小人工动作，保存断点并标BLOCKED。完成条件始终是原任务所需能力已经实际可用，而不是“已经帮你写了安装命令”。

## 12. 不偏离需求、不留无主尾项的完成责任

### 12.1 需求与实现双向核对

- 正向：每条本批需求／验收项都有任务、最终实现和有效证据；UI品质、错误状态及运行说明不能作为可随意删除的尾项。
- 反向：每个行为变化、页面、依赖与对外调用都能归属到已批准需求或必要工程任务；不能用某个Skill的默认模板替换用户需求，或借美化新增业务入口。
- 每任务结束、修复／换工具后及批次交付前核对差异；发现歧义先澄清，发现偏离先修正，不靠改需求文档使代码显得正确。
- 占位按钮、伪接口、TODO、未经批准的mock替代、残缺错误分支或未运行验证不能满足原验收；本批缺项不能自动挪到“以后优化”。

### 12.2 连续推进与可恢复停止

普通编码、UI打磨、安装、修复和复查属于执行责任，在既有权限／预算内自行完成。自动模式只要还有可执行的获准任务就持续调度，不在完成一个文件后结束并让用户反复“继续”；手动模式仍按明确任务推进，但每次留下完整断点，不能把单轮结束写成整批交付。

遇到可恢复故障先自动诊断和有界修复；确有预算、权限、外部可用性或需求冲突阻塞时安全暂停。**安全暂停不是放弃，静默停止、跳过失败或谎报完成才是失责。** 用户明确取消或暂停时必须尊重，不能以完成责任强行继续。

阻塞交接必须包含：未完成需求／任务、当前文件与证据版本、已尝试恢复及结果、剩余预算、未知副作用、自有进程、最小解除条件、下一条精确动作。能通过获准机制自动检测前提恢复时可在预算内接续，否则通知用户并保留状态；不能谎称离线会话仍在后台监控。

最终报告分开列技术完成、UI视觉验收、用户业务验收与发布状态。只有本批全部必需项满足，或用户明确批准范围变更并核对依赖后，才能宣称对应范围完成。工作流可用性须通过实际安装／调用、端到端任务与中断恢复试点验证，不能由这份规范保证外部服务永不中断或所有任务必然一次完成。
