## 2. 已确认的需求基线

### 2.1 主体、站点与库存

| 编号 | 已确认规则 |
|---|---|
| R01 | 采购方就是采购商；此前口述的“供应商”也指采购商。文档和界面统一称“采购商”，不新增供应商主体。 |
| R02 | 一个采购商对应多个加气站，一个站点只归属一个采购商。 |
| R03 | 一站一独立库存，没有公共库存、跨站共享库存、车队库存。采购商的跨站汇总视图不是共享库存。 |
| R04 | 每个采购批次只为一个指定站点补货；出气、预占和扣减都归属交易对应站点。 |
| R05 | CNG 与 LNG 在本站库存内分项记账，单位不同，不直接相加；“一站一库存”不要求把现有站点＋气种记录合成一行。 |
| R06 | 系统没有车队业务实体；车队人员也按散户下单、付款，不新增车队账户、优惠体系或专属结算。 |

### 2.2 管理员补货与后台分工

- 日常补货由 **H5 站点管理员** 在本站采购批次下录入。
- 页面参考 [design/prototypes/m-buyers.html](../design/prototypes/m-buyers.html)。参考批次、进气和库存调整的交互，不照搬其中多采购商选择等与新模型冲突的能力。
- 操作路径：**录入本次补货 → 本人确认弹窗 → 提交成功 → 直接增加本站库存**。
- 不需要其他人员审核，不设置待审批状态，不等待后台再次确认；取消确认不入库。
- 现有原型区分采购批次和分次进气记录，本轮不要求合并这两类数据。
- 开发启动时已确认超量到货采用方案 A：同批次累计到货不得超过采购数量，超出部分另建采购批次；M1 已拒绝超量，并通过真实MySQL并发、缩量竞争、回滚及HTTP验证；不再作为待选规则。
- 后台保留查看、调整能力，但主要用于查看和调整，不是日常补货主入口，也不是每笔入库的审核端。
- 入库必须记录操作人、批次和数量；已有库存调整仍填写原因并留流水。

### 2.3 司机与加气员主流程

```text
散户选择站点／枪号，输入金额
→ 下单时校验本站对应气种可用库存
→ 创建订单、付款
→ 本站唯一当班加气员在加气前扫码核验
→ 实际加气
→ 确认实际量
→ 完成核销、记录本站库存消耗及班次数据
```

- 同一个站点同时只有一名当班加气员可以核验、核销。
- 加气前核验 **不等于完成核销**，不在核验时标记完成或按实际量实扣。
- **库存充足性仅在下单时校验**；实际加气、核销时不再因库存量不足拦截，不要求系统处理现场缺货。
- 预占仍沿用原规则：支付成功后按 **原价金额 ÷ 销售单价** 计算的预计量预占，不按折后实付计算。本轮没有授权把预占提前到创建订单。
- 实际量记录与本站消耗口径继续保留；有足够批次余量时仍按到货 FIFO 追溯。
- 代下单仍是：员工当班扫码识别司机 → 创建待司机确认订单 → 司机确认、选择优惠券并付款 → 进入上述核验／核销流程。
- 非当班、跨站、未支付、已关闭、已退款、已核销等保护继续保留。取消库存量拦截不等于取消其他业务校验。

### 2.4 本期范围收敛

| 事项 | 本期口径 |
|---|---|
| 实际量与付款不一致 | 暂不做线上差额结算。加不下、少加或补加线下处理，不新增补款、差额退款、按实际量重算应付。 |
| 退款 | 完成核销前可以退款，不需要审批；不增加“已经开始加气不可退”的门槛。其他退款场景本期不考虑。 |
| 已完成订单退款 | 原后台部分／全额退款方案暂缓，不在本期重新实现。 |
| 数据录错 | 专项修改、更正流程延期，后续再在后台补功能；不删除现有正常查看、库存调整和留痕。 |
| 其他禁止扩展 | 不恢复钱包、充值、企业授信、车队业务、公共库存、第二人补货审批。 |

核销前全额原路退款、释放预占、有效券退回是现有方案细化，见 `Dev_Plan.md` §7.2；涉及退券等未明确细节时标注为方案默认，不虚构为用户新增答复。

### 2.5 其他沿用规则，不借优化扩大范围

- 按枪定价，后台维护枪价；原价金额、优惠、实付、预计量与确认量分别保存，不混用。
- 优惠券不叠加，成本由采购商承担；跨站使用的具体范围与核销前退券见现有方案及模块待处理事项，不自行新增营销体系。
- 采购付款只登记，不做审批；采购票据提醒对象是采购商，通知方式为短信。
- 拉卡拉商户号归属采购商；收银台还是 JSAPI 尚未选定。
- 动态码按常规设计为 30 秒刷新、60 秒有效、单次使用；不支持离线核销。核验上下文设计不能等同于放宽原动态码安全规则。
- 交班不需要第二人复核，仍保留本人当班和订单完成班次的记录。

## 5. 开发前必须解决的技术衔接

这是落实已确认需求的技术设计，不是重新讨论业务范围。M0 先写出方案及影响，再在相应模块落地。

### T1：核销不拦库存，但消耗不能丢

现代码不仅有 `checkAvailable`，还会在 FIFO 批次余额不够时抛错回滚。因此不能只删除前一个判断。

设计必须说明：当实际确认量超过可分摊的批次余量时，站点池、订单消耗、批次分摊和流水如何记账、如何重算，以及后续补货如何衔接。涉及负库存或未分摊消耗等新语义时，先说明方案和迁移影响，不偷偷选择。

不得虚构入库、借用其他站库存、少记实际消耗、静默修改历史余额，也不能把旧的库存不足阻断继续保留成新需求的变通实现。

### T2：下单检查不等于下单预占

需求仍是支付后预占。多个未支付订单可能分别通过下单检查，不能宣称一次检查就保证后续支付／加气库存始终充足。

下单校验、支付幂等、预占和核销记账要分别测试。不自行改为下单即占库存，不以支付后新增库存不足阻断绕开已确认的核销规则。

### T3：加气前短期码与加气后完成的衔接

已检查代码：

- `inspectRedeemToken` 读取有效动态码并返回订单。
- `StaffRedeem.vue` 保存同一个 `inspectedToken`，完成时再次提交。
- `redeem` 再调用 `validToken`，过期会拒绝。

动态码按已确认方案短期有效，实际加气可能超过有效期。需要设计服务端可验证、绑定订单／站点／操作人／班次的核验上下文，或说明其他满足已确认流程的方案。

不能无限延长动态码、跳过有效身份和订单状态校验，也不能为了避免过期在加气前直接完成核销。无论采用何种技术方案，退款或状态变化后，旧核验结果都不能使订单继续完成。

### T4：退款只做一个范围，但状态必须正确

只实现完成核销前退款，不加后台审批、已完成部分退款等能力。退款与完成核销必须互斥，渠道失败／处理中不得伪装为退款成功。

支付接口没有退款能力，需明确新增契约、mock 行为、真实渠道回执及幂等方式。真实拉卡拉接入方式仍未确定时，可以完成并验证 mock 业务链，但必须把真实资金退款标为未交付。

- 复用采购、库存服务和操作留痕；处理提交失败、重复点击和网络重试，不能靠前端禁用按钮保证只入库一次。
- 补齐站管接口权限与增量菜单／角色授权；不要用加气员“必须是本站唯一当班人”的门槛替代站管自身的管理权限。
- 后台不新增入库审核节点，不顺手扩展跨站档案、商户资料编辑。

**验收**：站管只能操作本站；非站管和跨站请求被拒；确认一次只增加一次库存；取消、失败不增加；数据刷新一致；无后台审核步骤。前端 build 与新增后端接口集成测试均通过，或如实列出环境阻塞。

### M2 · 下单库存校验与核销记账

**依赖：M0 的 T1/T2 方案，M1 提供补货闭环。**

- 主动和代下单创建入口统一校验本站对应气种可用量，计算使用原价金额／枪价。
- 保留支付后预占，不按实付折后金额减少预占，不偷偷改变预占时点。
- 按已评审的记账方案调整核销：不能因库存量不足拒绝，但站点池、批次、订单与流水必须可追溯。
- 若需新字段或账务结构，新增针对存量库的升级脚本并说明迁移，不重跑 `gas_schema.sql`。
- 调整与旧需求冲突的测试断言，保留未冲突的站点隔离、事务回滚、幂等及实际量记录保障。不得简单删除整个库存测试类。

**验收**：下单库存足够／刚好／不足均覆盖；优惠不改变预计量；两个站点互不影响；重复回调不重复预占；实际加气／核销不因库存不足阻断；实际消耗与账本一致；并发下单和重复核销语义有测试说明。

### M3 · 加气前核验、加气后完成核销

**依赖：M2；核验上下文按 T3 设计。**

- 核验成功展示待加气／已核对的业务信息，但不能标记订单完成或实扣。
- 加气后由当班人员确认实际量并完成核销；实际量与付款差额不在系统内结算。
- 处理加气时间超过动态码有效期的正常场景，不能靠无限延长动态码或提前核销解决。
- 重新校验完成时的身份、本站范围、本人班次和订单状态；退款、关闭、交班、重复提交后旧操作不能继续生效。
- 检查真实二维码展示和微信扫码路径，不以手工粘贴字符串或原型示意码代替扫码验收。

**验收**：扫码核验不扣库存；加气后只完成一次；超出原码有效期的合法完成可按方案操作；伪造／跨站／过期未核验码不可用；交班或退款后旧上下文不能核销；同站仍只有一名当班人。

### M4 · 核销前退款与相关券状态

**依赖：M2、M3；真实通道可单列资源依赖。**

- 订单详情增加仅适用于未完成核销订单的退款入口。
- 沿现有方案实现全额退款和预占释放，先核对必要的退券默认规则，再按明确口径处理。
- 扩展退款领域、通道契约、处理结果及操作记录；mock 与真实渠道分开实现和验收。
- 退款与核销并发互斥；重复请求、重复回调不能重复退款、释放预占或退券。
- 不新增完成后退款、部分差额退款、补款或审批环节。

**验收**：未核销可退款；已完成无退款入口且服务端拒绝；退款后不能核销；核销成功后不能发起本期退款；重复操作无副作用；渠道失败不能显示退款成功；mock 通过与真实资金退款通过分别记录。

### M5 · 后台查看／调整与权限、文案收口

**依赖：M1—M4 的相关数据与状态。**

- 后台以采购批次、库存、流水、订单及退款记录查看和既有库存调整为主。
- 查看中区分核验和完成、预计量和确认量、应付／实付与退款；采购商跨站汇总不成为共享库存。
- 保留调整原因、操作人和历史流水；不扩展延期的“录错原单后任意修改”功能。
- 对齐站管 H5 与后台的角色、数据范围、按钮文案，清理旧共享库存、第二人审批、已完成退款等不适用说明。
- 如新增报表指标，先核对时间口径，不把班次完成金额当作渠道到账金额；不顺手建设全套财务报表。

**验收**：列表、详情、导出遵守角色与站点范围；与 H5 数据一致；调整有留痕；看不到本期排除的业务入口。

### M6 · 模块集成、回归与交付核对

**依赖：M1—M5。**

至少串联：

1. 站管补货确认 → 本站库存增加 → 下单校验 → 支付 → 加气前核验 → 加气后完成 → 本站消耗／班次统计。
2. 支付后未核销 → 退款 → 预占释放 → 原核验结果不能完成订单。
3. 跨站访问、非当班操作、重放回调、重复入库、重复核销、交班后的旧请求。
4. 库存变化导致实际加气时账面不足，但核销按新规则完成且账务可追溯。
5. H5 页面失败与重试、刷新、前进后退、确认取消，避免保存失败却显示成功。

**交付分层**：

- **开发／mock 验收**：业务链、权限、账务和回归在隔离环境验证。
- **真实渠道验收**：另需确定拉卡拉收银台／JSAPI，验证真实支付验签、查单、退款结果、微信真机及短信资源。凭据由安全环境提供，不写入文档或会话。
- mock 通过不能把真实渠道栏标为完成，也不能直接宣布可生产上线。

## 7. 小范围验证命令与前提

命令应在对应目录运行。以下是现有入口；新增站管／退款测试后需在进度文档补充确切的新测试类和命令。

### H5：`h5/`

```sh
npm run build
```

需要 Node/npm 和依赖可用。当前没有 npm test、lint、type-check 脚本；build 不代替接口、数据库和浏览器验收。

### 后端：`RuoYi/`

仅编译打包、不执行测试：

```sh
mvn -pl ruoyi-admin -am -DskipTests package
```

`-DskipTests` 仍会编译测试，成功不代表业务测试执行过。

在用户确认的本地隔离 MySQL 测试库上，按改动选择：

```sh
mvn -pl ruoyi-admin -am -Dtest=GasInventoryServiceTest -Dsurefire.failIfNoSpecifiedTests=false test
mvn -pl ruoyi-admin -am -Dtest=GasOrderServiceTest -Dsurefire.failIfNoSpecifiedTests=false test
mvn -pl ruoyi-admin -am -Dtest=GasStaffServiceTest -Dsurefire.failIfNoSpecifiedTests=false test
mvn -pl ruoyi-admin -am -Dtest=GasH5AuthFlowTest -Dsurefire.failIfNoSpecifiedTests=false test
```

后端完整回归可使用：

```sh
mvn clean package
```

- 需要 Maven、JDK 17+、已配置的独立本地 MySQL；具体环境要求见 `AGENTS.md` 和部署手册。
- 这些测试会写数据库；部分并发测试独立提交并清理固定标识数据。不能指向生产或有价值的共享库。
- 确认目标 JUnit 测试实际执行且数量非零，不能用仅打包成功或 `bin/package.bat` 的跳过测试行为代替。
- 不为了修业务而顺手升级整个依赖栈；如果基线编译失败，先区分既有环境／依赖问题与本轮改动。

### 原型：仅在本模块确实修改原型时，从工作区根目录运行

```sh
node --test design/prototypes/tests/*.test.cjs
```

若修改 Tailwind 类或样式源，按 `AGENTS.md` 重建生成 CSS 并通过静态服务检查页面。不得手改生成 CSS，也不得拿原型测试替代后端事务测试。

数据库升级仅在确认目标与备份方案后执行；新环境初始化与存量升级分开。`RuoYi/sql/gas_schema.sql` 含删表操作，不可当作常规升级脚本重跑。

## 8. 跨 session 的执行与记录方式

使用 [模块开发进度.md](模块开发进度.md) 作为短上下文接力记录：

- 每轮开始：读取模块状态和上次结束记录，重新检查实际文件与 Git 状态。
- 每轮只处理一个模块；若有必要的前置改动，说明原因和边界，不借机重构其他模块。
- 开始编码前列出目标、文件、数据结构影响与验收用例；涉及 T1—T4 的方案应先明确。
- 结束时记录实际改动、SQL 是否执行、完整测试命令／结果、未验证部分、遗留阻塞和下一步。
- 模块未完成也要留下准确断点；不得把“已编写但未测试”记为“已验收”。
- 保存一个简短的下一会话任务，不依赖上一 session 的聊天记忆。需要提交或建立版本快照时由用户决定，不能自行把已有工作混成一次提交。
