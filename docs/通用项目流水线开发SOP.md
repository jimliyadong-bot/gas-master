# 通用项目流水线开发 SOP

> 版本：v1.4｜修订日期：2026-11-21｜适用：Pi中的新项目、已有项目、分模块迭代与跨窗口交接。
>
> **目的：你负责目标、关键决策和验收；AI负责梳理、落盘、按步骤实施、验证和交接。**
>
> 本文是操作手册。**本次修订时，三个`/flow-*`命令仍为拟新增，本轮没有安装Skill／模板或创建项目流程状态。** 这是编写时快照，不是以后判断安装情况的依据：先检查当前命令是否可用；未安装时用各节自然语言指令。文中的任务编号均为示例，须替换为当前项目实际编号。
>
> **共用质量规则：** [开发质量门禁与正确性验证标准](开发质量门禁与正确性验证标准.md)。风险分级、独立预期、红→绿证据、不变量和放行判据统一在该文件维护。跨目录使用／打包时一并携带或定位批准的版本；SOP不是代码100%正确的保证。
>
> **专业执行模板：** [专业任务模板与交接约定](专业任务模板与交接约定.md)，供AI按需读取UI、实现、QA及诊断片段，不要求用户管理12个Agent。

## 0. 先理解：流水线是什么

这里的“流式／流水线文件”是**可持续更新的项目工作记录**，不是把所有聊天复制到一个文件，也不是让AI无限连续修改代码。

固定流程：

```text
接入项目
  ↓
表达需求 → AI复述与追问 → 打磨业务规则 → 确认需求基线
  ↓
核对现状 → 拟定技术方案 → 拆分任务 → 审查／微调开发步骤 → 确认计划
  ↓
选择一个已获准任务 → 实现 → 验证 → 修复 → 当前模块验收
  ↓
下一任务／下一模块 → 整体验证与交付

任何阶段都可以：保存检查点 → 新窗口／新会话 → 读取检查点 → 核对现场 → 接着做
需求变化时：先评估影响 → 确认变更 → 更新基线／计划 → 再继续
```

### 三个原则

1. **文档是项目记忆，聊天不是唯一依据。** 新会话不需要旧聊天，只需要明确的状态入口和对应事实文档。
2. **一轮推进一个边界明确的任务。** 不把“继续”理解成一次做完整个项目。
3. **确认有范围。** 确认需求不等于确认技术方案；确认开发不等于授权执行SQL、删除数据、提交Git或上线。

### 谁做什么

| 事项 | 你负责 | AI负责 |
|---|---|---|
| 需求 | 说明目标、回答关键问题、确定本期范围 | 复述、发现冲突、补充异常场景、形成验收标准 |
| 方案／步骤 | 选择影响业务或数据的方案、确认开发顺序 | 分析现状、拆任务、说明风险和替代方案 |
| 实现 | 必要时提供安全环境与明确操作许可 | 在批准范围内改代码、做验证、处理失败 |
| 验收 | 确认是否满足实际使用要求 | 提供证据，不把未测／mock写成真实通过 |
| 交接 | 换窗口前发保存指令，新窗口发继续指令 | 保存可恢复状态，核对现场后接续 |

## 1. 一页操作总表

先照这个顺序走，详细指令见后续章节。

| 步骤 | 你做什么 | 产生什么 | 进入下一步的条件 |
|---|---|---|---|
| 1 接入 | 在正确工作目录打开Pi，要求初始化或接入 | 状态入口、规范与文档路径映射 | 项目目录和权威资料明确 |
| 2 描述需求 | 用业务语言说明“谁要做什么、解决什么问题” | 需求草稿、问题清单 | AI已正确复述主要目标 |
| 3 打磨需求 | 回答问题，确认范围、规则和例外 | 已确认需求基线、待定事项 | 当前模块所需规则不再含糊 |
| 4 拆分步骤 | 要求技术方案、依赖及任务拆分 | 开发计划与任务卡 | 每个任务可独立验证 |
| 5 微调计划 | 调整顺序、粒度、范围和验证方式 | 修订计划、技术决策记录 | 明确批准当前模块／任务 |
| 6 开发 | 执行当前获准任务 | 代码、必要文档、实际修改清单 | 实现完成，进入验证而非直接“已验收” |
| 7 验证修复 | 要求执行对应测试并报告证据 | 验证结果、缺陷／阻塞 | 必要检查通过，未覆盖项明确 |
| 8 模块验收 | 对照业务场景确认结果 | 验收结论、遗留项 | 用户确认，或明确记录保留条件 |
| 9 保存／换窗 | 保存检查点，再新建会话继续 | 新检查点、清晰下一步 | 文件确实保存且现场可对应 |
| 10 收口 | 全项目回归、运行与交付核对 | 交付清单、风险与运行说明 | 不把开发完成等同于生产上线 |

### 现在从哪里开始：不用先读完整本手册

| 你的情况 | 操作路线 |
|---|---|
| 想立刻开始，暂不安装 | 附上本手册 → 复制§3.3接入指令 → 按AI指出的当前阶段继续 |
| 想长期使用快捷命令 | 执行§2.2安装请求 → 按§2.3验收 → `/flow-init 目标` |
| 已经做了一半，换新窗口 | 旧窗口按§9.2保存 → 新会话按§9.4接续；不要重新init规划 |
| 只是修一个小问题 | 使用§3.1轻量模式，不必完整重走全项目需求和计划 |

**日常最短操作：确认当前范围 → 继续一个步骤 → 看真实结果 → 保存交接。** 每轮让AI最后只给出“当前状态、是否需要我确认、下一句该发什么”，不要求你记住所有模板。

## 2. 一次性准备：命令与Skill

### 2.1 先选一种使用方式

- **方式A：现在就用。** 无需预装工作流快捷命令，复制本SOP的自然语言指令；任务所需技能／扩展／验证工具仍按§2.5自动补齐。
- **方式B：常用推荐。** 安装一个全局Skill＋三个提示词模板，把长指令缩成快捷命令。安装完成后，两种方式执行的是同一套流程。

方式A首次在新项目使用时，先用`@文件路径`附上本手册，再发送接入指令。例如本机可引用`@D:/Project/workspace/gas/docs/通用项目流水线开发SOP.md`。这只是引用手册，**不切换当前工作目录、不继承gas项目的业务规则或数据库许可**；同一会话后续指令不用反复附上。

| 拟新增命令 | 定义 | 不应该做的事 |
|---|---|---|
| `/flow-init 目标` | 接入当前目录；识别已有规范、文档、进度；缺少时才建立最少文件 | 不重置已有计划，不自动开始编码或SQL |
| `/flow-next` | 按当前阶段继续：先接续未完成步骤；需求阶段澄清，方案阶段设计，获准后才编码，详见§7.1 | 不跳过当前任务，不自动批准方案或跨模块扩范围 |
| `/flow-save` | 保存事实、证据、未完成操作和下一步 | 不承诺尚未执行的测试通过，不自动Git提交 |

首次需求讨论、计划微调仍可直接自然语言进行，不需要为每一个动作增加命令。

### 2.2 安装时，给AI这一段指令

这是供以后执行的安装请求；**本SOP的编写不等于已经执行安装**。

```text
请先阅读docs/通用项目流水线开发SOP.md；如果它不在当前目录，
使用我通过@附上的手册路径；两者都没有时先询问位置，不凭空猜。
把这份SOP落地为通用Pi工作流：一个全局project-workflow Skill，
以及flow-init、flow-next、flow-save三个全局提示词模板。

先阅读当前安装版本的Pi skills、prompt-templates、configuration等相关文档。
只创建或针对性修改所需文件；同名文件已存在时先检查，不覆盖未知配置。
三个模板应明确要求读取同一份Skill规则，不各自复制一套可能分叉的规则。
一并读取《开发质量门禁与正确性验证标准》，将批准版本作为共用资源打包，
任务记录风险与质量卡；不要在手动版和自动版各维护一套不同门槛。
一并携带《专业任务模板与交接约定》的批准版本，按任务加载相关片段并核对交接，不整套加载岗位提示词。
不要假定模板内再写一个/skill命令就一定会二次展开；按本机文档支持的方式实现。
全局Skill运行时不依赖gas项目里的手册绝对路径，必要参考资料放到Skill自身目录。
检查命令／Skill是否同名冲突；不得通过覆盖其他资源消除冲突。

必须支持：
1. 任意工作目录独立运行，核对目录、已有AGENTS和嵌套仓库边界。
2. 新项目初始化；老项目复用现有需求／计划／进度文档，不重新规划已完成内容。
3. 需求确认、方案确认、任务拆分与微调、单任务开发、验证、验收、交接。
4. 权限按项目与具体目标记录，不从其他项目继承数据库或上线授权。
5. flow-save保存事实后，flow-next在新会话核对现场，优先接续当前未完成步骤。
6. 需求／方案阶段尚无任务卡时，继续澄清／设计，而不是凭空编码或反复报缺任务。
7. init重复执行只补缺项；不得重置现有进度、确认或任务编号。
8. 缺必要批准、证据不明或有其他窗口同时写入时停止相关操作并说明。
9. 涉及前端时落实共用UI标准，设计、真实预览、视觉审查和功能回归都要进入任务。
10. 按已有能力安装授权自行补齐并调用所需技能／扩展／工具，完成可用性验证再接续。
11. 保存未完成项与恢复动作，双向核对需求和实际改动，不把缺项自动延期。

这是手动触发的轻量版，不要声称具有自动上下文监测、强制进程锁或自动创建新会话。
不要把本项目的技术栈、数据库地址或业务规则写死到全局Skill。
不要读取auth.json或输出秘密；不要改业务代码、数据库、模型或代理配置。
完成后提供模拟目录验证、文件清单、回退方式，以及一次/reload生效说明。
```

默认全局位置：

```text
~/.pi/agent/
├─ skills/project-workflow/SKILL.md
└─ prompts/
   ├─ flow-init.md
   ├─ flow-next.md
   └─ flow-save.md
```

Windows默认是`C:\Users\你的用户名\.pi\agent\`。如配置了其他agent目录，应使用实际目录，不机械复制别人的用户名。

安装后在当前Pi输入一次`/reload`；新启动的Pi会重新发现资源。在命令补全中确认三个命令存在后，再使用快捷命令。

### 2.3 安装验收：看见命令不等于交接已经能用

先在一个专用临时目录演练，任务只用“编写一份测试说明文档”，不连接数据库或外部渠道。由你手动开新会话，不自动启动额外Agent。

| 检查 | 应看到的结果 |
|---|---|
| `/flow-init 编写测试说明` | 识别临时目录，建立最少记录，先澄清目标而不是自行扩写 |
| 再次init同一目标 | 原确认、编号和记录保留；目标变化则先讨论变更，不清空重建 |
| 未确认方案时`/flow-next` | 只澄清／设计或列出待确认项，不越过门槛改实现文件 |
| 已确认小任务后保存、`/new`、next | 只凭状态与文档接续，目录、任务、批准范围正确，不重做已经完成的步骤 |
| 当前任务未完成或验证失败 | 先处理当前断点，不直接选择下一任务；结果未知的写入先核对 |
| 另一个空目录中next | 不读取上一项目的进度／授权；提示先接入当前目录 |

以上是**安装后待执行的验收清单**。仅检查Markdown或做模拟测试，不能宣称新会话恢复已经实测通过。快捷入口失败可回到自然语言方式并记录限制；这不允许省略原任务必需的浏览器、测试或审查能力，仍按共用标准补齐。

### 2.4 轻量版的能力边界

Skill／模板是统一工作指令，不是强制执行器。模型可能遗漏步骤，因此必须有落盘检查和阶段门槛。

- 不会因为上下文达到某个百分比就保证自动保存。
- 不会自动加进程锁、自动打开新窗口或自动接管另一个会话。
- 不保证整个任务无人值守；关键决策和新风险操作仍需要你确认。
- 如果以后需要自动阈值提醒、按钮式切换或严格状态校验，再设计扩展／脚本增强，不在第一版承诺这些能力。

### 2.5 必要技能／扩展由AI安装和调用

统一遵守 [能力自动补齐闭环](开发质量门禁与正确性验证标准.md#capability-bootstrap)：先复用，确有缺口再自行检索、审查、安装、加载、真实调用和验收，不只交给用户一串命令。技能说明需实际读取；安装成功不等于当前会话已可用。

用户已经明确允许本任务自行安装／调用时，记录并沿用，不再逐包询问。首次缺少这类许可时，将来源类别、安装范围和预算与计划一并确认，例如：

```text
本批必要的免费本地技能、扩展和工具，请自行选用并完成安装、加载与实际调用验证。
先复用现有能力，核对来源和兼容性；优先项目／隔离目录，记录版本、变更和回退方式。
已批准类别内不逐个包询问；不得覆盖已有资源、擅自全局升级或降低验收要求。
付费、提权、新凭据、私有数据外传、模型供应商变更及生产操作仍按各自许可执行。
安装与修复使用本任务已确定的预算；遇到真正无法代办的步骤，只告诉我最小所需动作。
```

手动模式并不意味着用户需要手动安装一切；但不能宣称Skill拥有自动换会话或宿主不支持的热加载能力。失败时先在许可内恢复／等价替代，仍无法解决则保存可恢复阻塞，不伪造能力可用。

## 3. 工作流文件如何生成

### 3.1 全新项目建议结构

```text
当前工作目录/
├─ AGENTS.md                         已有则遵守，不擅自覆盖
├─ .pi/workflow/
│  ├─ state.md                       当前检查点入口与下一步
│  └─ history.md                     追加式执行／交接记录
└─ docs/workflow/
   ├─ requirements.md                本期需求、规则、验收标准
   ├─ decisions.md                   已确认决策、依据、待定事项
   └─ plan.md                        模块、任务、依赖、文件范围与验证计划
```

**不是让你手工写五个文件。** 你给接入指令后，由AI按阶段生成内容；没有形成的结论必须标待定，不能为了填满文件而编造。

职责保持单一：需求规则放requirements；决策放decisions；任务定义放plan；实际执行与证据放history；state只保留当前入口、检查点和下一步，不复制整份历史。

**小任务可用轻量模式：** 一个范围明确的修复／文档调整，可以只用state记录目标、确认、步骤、验证和交接；history角色映射到该文件的历史记录区，不必创建五个空文件。若已有进度文档，直接复用它。任务扩大到多个模块或长期迭代时，再把内容拆分到对应文件，保留旧记录与引用。

### 3.2 已有项目的接入原则

先扫描已有规范与文档，再建立角色映射。例如：

| 工作流角色 | 可复用的已有文件 |
|---|---|
| 需求依据 | 现有PRD、产品需求说明 |
| 决策依据 | 已有方案／业务决策记录 |
| 开发计划 | 已有分模块计划、任务清单 |
| 执行记录 | 已有开发进度、验收记录 |
| 会话入口 | 已有交接文档，或新增一个简短state索引 |

每种事实指定唯一权威来源。旧文档有冲突时记录冲突及依据，不能悄悄选择有利于实现的版本。state是恢复索引，不凌驾于已确认需求或项目规范；冲突不能只按文件修改时间决定。阶段完成时先更新权威记录，再刷新state中的摘要和引用。

**不要为了遵守目录示例复制第二份PRD、PLAN和进度表。** 已有文件可以继续留在原位置；state只记录映射。

### 3.3 通用接入／生成指令——未安装命令时直接复制

```text
请为当前工作目录接入可跨会话恢复的开发流程。当前目标是：【填写目标】。
这一步只做项目识别与文档接入，不修改业务代码或执行数据库写操作。

先读取本目录适用的AGENTS和已有需求、计划、进度、交接文档。
确认工作目录、仓库边界、当前完成状态和待确认事项。

若是新项目，按SOP逐步生成需求、决策、计划、状态入口和执行记录。
若已有这些资料，直接建立权威路径映射，不覆盖、不复制第二套进度。
状态入口使用.pi/workflow/state.md；如项目已有强制入口，先说明如何兼容。

最后告诉我：当前所处阶段、哪些文件已创建／复用、还缺哪些关键答案，
以及我接下来只需要发送的那一句指令。不要伪造确认或测试结果。
```

安装命令后可用：`/flow-init 【目标】`。已接入项目重复init只补缺项；目标改变时走变更流程，不重置原计划。

### 3.4 目录与文件保存约定

- 接入时明确“工作流根目录”及各子工程的构建目录。嵌套Git仓库不能混用命令目录；从子目录启动却发现父级入口时先确认归属，不自动接管另一个项目。
- 恢复时先读state、适用规范和当前任务相关片段；历史按需检索，不把全量日志重新塞进上下文。state建议保持约1—2屏的核心摘要，较长证据放到引用文档。
- 检查`.pi/workflow/`是否被忽略。**文件在本机存在不等于已经进入Git或备份**；同一工作目录的新会话可读取它，新克隆／另一台机器未必有它。
- 是否纳入版本控制或另行安全备份由项目决定，不擅改`.gitignore`、强制添加或提交。换机器须带上状态及其引用的项目文件，重新核对环境；绝对路径和临时证据可能失效。

## 4. 定需求与打磨需求：先把“做什么”讲明白

### 步骤4.1：表达原始诉求

不要求你先写专业PRD。可以直接说：谁使用、现在哪里不方便、希望怎样操作、这次先不做什么。

复制给AI：

```text
先帮我定需求，不写业务代码。

项目／功能：【名称】
使用者：【谁使用】
当前问题：【现在怎样，哪里不方便】
期望流程：【用户从哪里开始，操作什么，得到什么结果】
本期想做：【范围】
本期不做：【排除项；不知道可先空着】
现有资料：【文档、截图、原型或说明；没有就写没有】

请先复述你的理解，区分事实、假设和待确认项。
每轮优先问3—5个最影响范围／流程的问题；不要求一次问完所有细节。
```

**AI应交付：** 一段业务理解、主流程、本期范围、带编号的问题清单。此时只是草稿，不标“已确认”。

### 步骤4.2：打磨规则与边界

你逐条回答问题；AI把答案写入需求／决策文档，再检查异常分支。

```text
我的回答是：
Q-001：【答案】
Q-002：【答案】
Q-003：【暂缓／需要你给出选项】

请更新需求草稿，并检查角色权限、数据归属、重复操作、失败恢复、
数量／金额边界和本期不做的内容。
还没确认的规则继续标待定，不要擅自补成“默认已同意”。
已经回答的问题不要反复问，除非发现了新的冲突。
```

**判断是否打磨够了：** 对当前模块至少能回答“谁能做、处理什么、何时生效、失败怎么办、什么算成功”。

### 步骤4.3：确认需求基线

先让AI给出简短确认清单，然后你明确确认范围：

```text
确认需求基线B1中的R-001至R-008，本期不做项保持不变。
Q-009仍待定，涉及它的任务暂不能实施；不受影响的部分可以继续做方案。
请保存确认依据和版本，进入技术方案与开发步骤梳理，暂不编码。
```

上面的编号是示例，使用AI实际输出的编号。不要未经查看就照抄“全部确认”。

**退出条件：** 需求文档有版本、已确认规则、待定规则、本期不做项，以及可观察的验收标准。对小功能可以很短，不追求文档页数。

关键样例按共用标准的 [独立预期规则](开发质量门禁与正确性验证标准.md#independent-oracles) 固定来源与判断依据；不能直接用实现输出给自己出答案。

涉及前端时，按 [UI审美与专业度标准](开发质量门禁与正确性验证标准.md#ui-quality) 明确终端、风格与设计依据。AI主动给代表页面方案／预览，方向确认后批量实现；已有明确设计直接复用，不让用户逐个决定字号间距。功能正确与视觉专业度均为验收内容，不能只写“页面美观”。

## 5. 梳理开发步骤：把需求变成可执行任务

### 步骤5.1：先对照现有代码，不凭想象拆计划

```text
请基于已确认需求和当前源码，梳理开发方案与步骤，先不改业务代码。

输出：
1. 已有能力、缺口与冲突；每项给出相关文件或依据。
2. 关键技术方案与替代方案，标明哪些需要我确认。
3. 按依赖排序的模块，再拆成单次会话能推进的任务。
4. 每个任务的目标、前置条件、允许改动范围、明确不做项。
5. 每个任务的验证办法、成功标准、数据／迁移风险和回退考虑。
6. 需求→任务→验收场景的对应关系；每条本期已确认需求都应有实现及验证去向。
7. 按共用质量标准给出风险等级、适用检查、独立预期和任务质量卡；不强加无关重型测试。
8. 前端安排设计基线、代表页、页面／状态／终端矩阵、视觉审查和功能回归。
9. 列必要能力及可用证据；缺失能力按已有安装许可自行补齐，把准备和故障恢复计入计划。
10. 按需选专业模板，明确产物位置、版本、产出与接收检查责任；复用现有任务卡，不新增一套项目文档。

任务使用稳定编号，例如M2-01，后续插入任务不随意重排旧编号。
计划只是未来安排；不要把预计测试写成已通过。
```

任务粒度建议：一个清晰行为＋可定位的文件范围＋一组对应验证。一个任务可以跨前后端，但不能同时含多个互不相关的大改造。

可以直接在计划中用一行记录`R-001 → M2-01 → 正常／越权／重复请求场景 → 验证证据位置`，不必再造一份大表；证据未产生时标“待执行”。需求延期要明确移出本期，不能因为没有任务对应就静默遗漏。

### 步骤5.2：检查任务是不是“能交给新窗口执行”

让AI自查：

```text
请审查刚才的计划：
- 是否遗漏权限、重复提交、异常、并发、数据清理或文档任务？
- 是否把尚未确定的技术选择写成了既定方案？
- 是否存在依赖倒置、任务过大、无法独立验证或不可回退的问题？
- 新会话只读任务卡和关联文档，能否知道从哪个文件开始、做到哪里停止？

先列出建议修改和影响，不直接扩大范围。不要自行调用额外Agent。
```

计划可以先由当前AI自查；审查强度按共用 [风险分级](开发质量门禁与正确性验证标准.md#risk-levels) 与质量卡确定。需要独立审查时，由获准的独立会话或合适的人工审查完成；未获额外Agent许可就先提出需要，不能静默委派或用同一实现上下文自查冒充独立Review。

## 6. 微调步骤与确认计划

### 步骤6.1：你用业务语言修改，不必亲自重写计划

例如：

```text
请微调计划：
1. 先做【任务A】，再做【任务B】。
2. 【任务C】拆成可独立验证的两步。
3. 本轮只做【范围】，把【另一项】移出本轮。
4. 保留必要的权限／事务／回归检查，不要为了加快进度删除它们。

请先评估依赖和风险；若我的顺序会导致返工或数据风险，说明理由并给替代顺序。
展示计划P1→P2的变更摘要，等待我确认，不直接开始编码。
```

### 步骤6.2：确认当前可执行部分

```text
确认计划P2，以及技术决策D-001、D-002。
本轮批准实施M2-01，范围按任务卡，不提前实现后续模块。
D-003仍未决定，依赖它的任务保持设计待确认。
请保存本次确认，再开始M2-01。
数据库、对外渠道、删除、Git提交和上线操作仍按各自明确授权执行。
```

**确认整个顺序，不等于确认所有未来细节。** 对当前任务不构成依赖的问题可以留到对应模块，不必把所有远期问题一次问完。

也可以一次批准明确版本下的一组任务，再逐次`/flow-next`执行其中一个，不必每轮重新批准未变化的内容。仅批准一个任务时，不能顺势实施其余任务。前置条件要写明是“技术验证通过”还是“用户验收通过”；不得把整个模块的人工验收门槛强加给每个小任务，也不得跳过明确要求的人工验收。

### 开发中途改变需求怎么办

不要只说“顺便加一下”就直接实现。使用：

```text
提出变更CR-001：【变化内容】。
先评估它对已确认需求、现有代码／数据、当前任务和测试的影响。
区分：仅文案／布局微调，还是业务规则／数据结构变更。
给出建议和最小调整范围；等我确认后更新需求版本、决策和计划。
不要把历史通过结果直接套到变更后的版本上。
```

需要新需求基线时记录旧版本被哪些条目替代，不抹掉历史依据。仅文案调整也要跑受影响检查，但不必重新召开全项目需求讨论。

## 7. 分步开发：每一轮照这个小循环做

### 步骤7.1：按当前阶段继续，先接续再选新任务

安装命令后：`/flow-next`。同一命令在不同阶段有不同动作：

| 当前情况 | 本次next做什么 |
|---|---|
| 需求还未确认 | 继续复述、打磨和提出关键问题；尚无任务编号是正常情况 |
| 需求已确认，方案／计划未批准 | 梳理方案、任务或处理计划微调；不编码 |
| 当前任务进行中／实现待验证 | 优先接续未完成实现、测试或缺陷修复，不跳到下一任务 |
| 当前步骤阻塞／关键决定待确认 | 先在许可内诊断／恢复；确需决定时说明最小解除条件，只推进已明确允许且不受影响的工作 |
| 当前任务满足退出条件 | 核对授权与依赖，再选择下一项；模块需验收时先给验收清单 |
| 本期已完成 | 给交付摘要，不自行追加新需求或新模块 |

未安装时：

```text
读取当前工作流状态入口、项目规范和当前阶段所需资料，核对现场。
先接续当前未完成步骤；没有未完成断点时，才选择下一项已获准且依赖满足的任务。
需求阶段继续澄清，方案阶段继续设计；尚未拆任务不等于状态丢失。

本轮只推进一个明确边界。开始前简要说明当前阶段／任务、范围、验证和停止条件。
若目录不符、相关批准缺失或操作结果未知，先停止相关实现／写入并说明。
不要重做已完成任务，不清理或覆盖工作区已有修改。
```

进入实现阶段后，AI每轮应执行：

```text
核对目录与任务 → 核对批准／依赖 → 标记进行中
→ 补齐并实测必要能力 → 小范围实现 → 行为验证／适用UI实览与审查
→ 如失败则定位／修复／重测 → 双向核对需求与改动
→ 记录真实结果及未完成项 → 保存检查点 → 告知下一步
```

AI按 [专业任务路由](专业任务模板与交接约定.md#task-routing) 选择当前所需片段；同一会话切换职责不冒充独立Review。跨步骤、职责或会话时按 [交接约定](专业任务模板与交接约定.md#handoff) 实际读取产物并检查版本，不仅转述上一轮“已完成”。前端先核对设计与接口／状态契约，做通代表性闭环再扩展；纯后端任务不强加UI。

### 步骤7.2：明确测试环境授权

只有确实需要写库／外部操作时才用这一段。**先核实再填写，不能把模板当作“环境安全”的事实声明。**

```text
目标环境：【地址／端口／库名或外部服务目标】。
数据性质：【已确认专用测试数据／存在共享或正式数据／尚未核实】。
授权操作：【具体任务、允许创建和按ID清理的专用记录范围；或暂不授权写入】。

请先只读核对实际连接目标；若目标不符或数据性质尚未核实，停止写入并说明。
本授权不含清空整库、重跑删表初始化、新迁移或操作正式数据。
凭据通过本机安全配置提供，不在聊天或文档中展示。
目标、环境或操作范围改变时重新确认。
```

同一目标、同一已批准范围跨会话可沿用已记录的授权，不机械重复询问；但必须重新核对实际连接目标。**不得把另一个项目的许可当作本项目许可。** 新迁移、批量删除、正式发布等超出原范围时仍要确认。

### 步骤7.3：完成代码不是完成验收

```text
请按本任务已审核的风险等级与质量卡执行适用验证，并核对共用质量门禁。
逐项记录PASS、FAIL、NOT_RUN、BLOCKED或有理由的NOT_APPLICABLE，不能只给总评。
报告工作目录、完整命令、实际执行数量、结果和证据位置。
区分静态检查、构建、单元、API mock、真实HTTP／数据库和真实外部渠道。
缺工具先按授权自行安装／调用验证；仍无法执行时说明具体阻塞，不把预期结果填成通过。
前端须实际查看运行页面／截图，按共用UQ标准记录视觉、交互和适配证据；构建成功不替代UI验收。
只检查本轮白名单文件，不输出无关配置或秘密。
```

注意：构建可能触发数据库测试或其他副作用，不能仅凭命令叫“build/package”就认定安全。先读项目自己的验证约定。

推进前按 [QG-01—QG-08](开发质量门禁与正确性验证标准.md#release-gates) 核对；本模式是人工／当前会话核对记录，不宣称机器门禁已经实现。缺环境、必需项未执行或证据过期时不能写成技术通过。

### 步骤7.4：验证失败时

- 原因不明或反复出现：使用 [根因诊断模板](专业任务模板与交接约定.md#debug-task)，区分事实／假设，用安全最小实验取证；诊断意见交付不等于缺陷关闭。
- 可定位且不改变已确认方案的问题：按共用 [红→绿要求](开发质量门禁与正确性验证标准.md#red-green) 保存目标缺陷复现、修复和受影响回归证据；不能用环境报错冒充RED。
- 无法安全复现：记录限制并提出按风险审核的替代证据方案，不破坏用户现场或伪造复现通过。
- 需要改变业务规则、迁移方案或权限范围的问题：停止，进入变更／确认流程。
- 缺环境／工具：先在已有许可内自动诊断、安装／修复并实测；确实不可获得或需新权限时才标阻塞，保留已尝试项和精确恢复动作。
- 旧测试与新确认需求冲突：先说明冲突和需求依据，再调整测试；不能简单删断言让它变绿。

## 8. 模块验收与进入下一模块

### AI先提交验收摘要

你可以发：

```text
请按本模块验收标准与共用质量门禁逐项汇总，关联当前质量卡版本：
已完成且有证据、实现但未验证、明确未做／延期、仍失败／阻塞。
列出真实验证层次，不只给“构建成功”。
检查未完成项是否影响下一模块，给出建议，但不要替我确认验收。
```

### 你再明确结论

正常通过：

```text
确认本模块验收通过，依据刚才列出的验收项和证据。
请记录确认，进入下一模块的方案确认；后续待定方案不自动视为批准。
```

有保留项：

```text
确认【已验证范围】，保留【未完成项】为待办。
这些项【影响／不影响】下一步，理由是【说明】。
不得将整个模块标为已验收；先推进不受影响的【具体任务】。
```

当前项目规定了状态名称时必须沿用。通用项目可采用：**待开始、设计待确认、进行中、实现待验证、已验收、阻塞**。状态词必须说明对象是任务还是模块；技术验证通过后可满足任务卡的退出条件，但不得因此自动把整个模块标成用户已验收。

已验收必须说明验收范围。mock闭环通过不是渠道上线通过；一个模块通过不是整个项目已交付。

## 9. 保存交接与新窗口恢复

### 步骤9.1：什么时候保存

- 每个任务结束后。
- 修改需求／计划、做出关键决策之后。
- 完成有副作用的操作后，尽快记录结果及可核对ID。
- 准备关闭窗口、换会话或上下文已接近上限时。建议70%—80%附近主动保存，不必等到84%以后。

轻量版不保证自动监测；发现占用较高时由你发保存指令。

### 步骤9.2：旧窗口保存

安装后：`/flow-save`。

未安装时：

```text
暂停新增实现，保存交接检查点。
写入前先复读当前检查点；若已被其他窗口更新，停止覆盖，先核对并协调。
再更新实际需求／决策／计划变更、追加执行记录，最后更新状态入口并复读核对。
记录当前任务、已经执行的操作、实际验证、未完成或结果不确定的操作、
已有工作区修改、尚在运行的本轮进程，以及新会话第一步应该做什么。
不记录密码、JWT、完整环境配置或未脱敏日志。

给检查点一个唯一编号，记录它接续的上一个检查点，并告诉我文件是否真的保存成功。
若多个文档角色映射到同一文件，合并更新并保留已有历史，不用旧缓存覆盖新记录。
不要只回复“已经记住”，不要把尚在运行的测试记为通过。
```

推荐写入顺序：事实文档 → history → state。**这不是跨文件事务**：中断后仍需核对引用的版本／检查点是否一致；保存失败不能宣布交接完成。写前复读也不等于强制锁，仍按单写入窗口约定操作。

写入成功后再复读状态和关键引用，确认编号、任务、批准版本与实际结果一致。旧记录错误时新增更正记录并引用旧编号，不悄悄抹掉原结论。

### 步骤9.3：打开新会话

在新终端中执行以下PowerShell示例，不是把它发给旧会话的AI来改变目录：

```powershell
Set-Location 'D:\你的项目目录'
pi
```

也可以在同一目录的Pi里使用`/new`。Pi会话的工作目录固定；让AI在工具里执行`cd`不会把现有会话变成另一个项目的会话。

为了降低上下文占用，不用`pi --continue`、`/clone`或`/fork`代替文件交接：这些操作会继续或携带旧历史，不是仅加载精简状态。

### 步骤9.4：新窗口继续

安装后只输入：

```text
/flow-next
```

未安装时输入：

```text
请读取当前目录适用的AGENTS、.pi/workflow/state.md及其引用的权威文档。
若状态入口不存在，先查项目已有交接／进度入口；没有就问我，不凭空猜任务。
按需读取当前任务相关片段，不一次加载全部历史。
核对当前目录、检查点、文件现场、测试证据和未完成操作；证据丢失或版本不符时明确说明。
先用简短清单说明“接续哪个阶段／任务、哪些已完成、第一步做什么”，
然后优先接续当前断点；需求／方案阶段继续澄清，获准且前置条件满足才实现。
不要重新执行结果未知的写入，不重复询问已确认且仍适用的决定。
```

**正确恢复后的第一句话应类似：**“已接续检查点C-007，当前M2-02，M2-01证据已核对；本轮先补X验证，不重复建表／入库。”这只是示例，不是当前项目结果。

## 11. 卡住、中断、过载或多窗口时怎么做

| 情况 | 正确处理 |
|---|---|
| 模型过载 | 让客户端按已配置策略重试；这与工作流检查点是两回事，不保证尚未保存的交接已落盘 |
| 工具结果返回前断开 | 先查进程、文件、测试报告或业务幂等结果，再决定是否重试；不能直接重复写库 |
| 状态文件缺失 | 查既有交接／进度资料并询问；没有依据时不猜当前任务 |
| 状态与代码不一致 | 暂停新增写入，列差异、定位最后可信检查点，修正记录后继续 |
| 测试跑不了 | 标阻塞和前提，不宣称“应该通过” |
| 新窗口目录不对 | 停止，回到对应目录；不把另一个项目的进度与授权带过来 |
| 项目移动到新机器 | 重新绑定目录，检查工具、环境和授权适用性；不复制秘密或直接沿用旧连接 |
| 两个窗口同时干同一个项目 | 先决定一个写入窗口；轻量版没有强制锁，不能仅凭state里写了名字就保证互斥 |
| 需要并行工作 | 另行设计任务划分、独立工作区／锁与合并规则；不要默认开启多Agent |
| 上下文已高且保存失败 | 停止新实现，先保存最小事实检查点；必要时手动保留下一步指令，再新建会话核查 |

### 防止“看似流水线，实际失控”

- 不自动清理、reset、覆盖未知修改或提交Git。
- 不把“整个本机是测试环境”扩大解释为可操作远程服务或正式库。
- 不用重导初始化、清空提交凭据、删除账本来恢复失败任务。
- 不全仓输出配置差异；**`git diff --check`也可能回显敏感行**，检查必须限定已知文件。
- 不把保存交接等同于执行了Git提交、外部备份或远程同步。
- 不把用户说“继续”解释为批准一个此前未解释清楚的新业务方案。

## 12. 最终交付怎么收口

所有当前范围模块完成后，再执行整体检查，不把最后一个任务完成当作全项目交付。

```text
请按已确认需求基线和本期范围做最终交付核对：
列出已验收模块、未完成／保留项、回归证据、运行与部署方法、迁移注意事项。
确认新会话或接手者能依照文档启动和验证。
明确哪些只是mock、哪些有真实环境证据，以及尚需哪些正式环境资源。
只准备交付材料，不自动提交、发布或执行生产操作。
```

交付最少包含：需求范围、实际功能清单、启动／构建／验证命令、配置项名称与安全配置方式、必要迁移说明、已知限制及下一阶段入口。涉及前端另附设计依据、最终截图及UQ审查；补齐过能力则附来源／版本、实际调用证据和回退方法。

按 [完成责任与需求双向核对](开发质量门禁与正确性验证标准.md#delivery-convergence) 收口：每条需求有最终证据，每项改动有批准依据。本批遗漏不能自动改成“下次优化”；单轮手动任务结束不等于整批完成，暂停须留下未完成项、已尝试恢复、剩余预算与下一条动作。

## 14. 每轮结束只看这六项

- [ ] 我知道当前需求／计划版本，以及本轮只做哪个任务。
- [ ] 关键决策与操作许可有明确范围，没有把待定当确认。
- [ ] 实际修改、数据操作和未完成事项已经记录。
- [ ] 测试实际执行且符合任务风险／质量卡，独立预期、缺陷证据和适用门禁可核对。
- [ ] 检查点已保存并复读，新窗口知道第一步做什么。
- [ ] 没有把实现、测试通过、用户验收和正式上线混为一谈。

**记住最简单的节奏：先说清楚 → 确认当前范围 → 一步实现 → 一步验证 → 保存 → 新窗口继续。**
